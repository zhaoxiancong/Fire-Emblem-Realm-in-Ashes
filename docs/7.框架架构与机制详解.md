## 1. 一句话回答：这个框架和《圣魔之光石》是什么关系

**框架就是《圣魔之光石》美版的完整反汇编 + 一套现代化改造工具链。**

更准确地说，分三层关系：

| 层次 | 关系 |
| --- | --- |
| **血统上** | 它是《Fire Emblem: The Sacred Stones》(USA) 的**反汇编项目** `fireemblem8u` 的下游分支 |
| **技术上** | 把原版用 agbcc（2001 年的古董编译器）编译的产物，**重写成可用现代 GCC 编译的 C/汇编源码** |
| **法律上** | 它**不含**任何原版 ROM 数据，是**源码级重建**；构建产物与原版**不要求逐字节相同** |

### 1.1 三条硬证据

**证据一：ROM 头身份字段。**

`src/rom_header.s`：

```asm
RomHeaderGameTitle:  .ascii "FIREEMBLEM2E"   @ 原版美版标题
RomHeaderGameCode:   .ascii "BE8E"           @ BE8E = Fire Emblem 8 English
RomHeaderMakerCode:  .ascii "01"
```

`BE8E` 是任天堂给《圣魔之光石》美版分配的**官方产品码**。框架保留了这个码，说明它重建的目标就是这款游戏。

**证据二：README 自述。**

> A **Fire Emblem: The Sacred Stones (GBA) expansion framework**, built and released with a modern `arm-none-eabi` GCC/AAPCS toolchain.
>
> The build does **not** require the original ROM — a `baserom.gba` is only used by `asmdiff.sh` for disassembly comparison.

**证据三：需要原版 ROM 吗？——不需要。**

框架的构建**完全不需要原版 ROM**。原版 ROM 只在一种场合被用到：`asmdiff.sh`，用于把框架编译出的汇编与原版做**逐字节比对**（验证反汇编的还原度）。这是可选步骤，与你的改版开发无关。

### 1.2 与《圣魔之光石》的谱系图

```
《圣魔之光石》美版卡带（2004）
        │  ROM 二进制
        ▼
fireemblem8u  反汇编项目（社区）
        │  逆向出 C/汇编源码，用 agbcc 编译，逐字节还原原版
        ▼
fireemblem8-expansion  本框架（laqieer）
        │  ① 换用现代 arm-none-eabi GCC/AAPCS 编译
        │  ② 加入 JSON 数据层、本地化层、扩展机制层
        │  ③ 保留 agbcc 路径作为"档案车道"
        ▼
《山河烬 / Realm in Ashes》  你的改版
```

### 1.3 这个关系对你的三个实际影响

| 影响 | 说明 |
| --- | --- |
| **画风 100% 还原是白送的** | 因为素材本来就是原版的——地图、立绘、战斗动画、字体、音效全在源码里。你不需要美术外包就能有正统 GBA 火纹观感。 |
| **你能学到的是真东西** | 你手上是 403 个 C 文件、172 个头文件的**完整游戏源码**，不是什么黑盒工具。想看战斗公式就看 `src/bmbattle.c`。 |
| **但你要注意"原版包袱"** | 所有原版角色（艾莉卡、塞思等 94 名）都在数据里。你的 22 名原创角色要和它们共存，需要理解 `fullCoverage` 机制（见 §5.3）。 |

### 1.4 一个常见误解要澄清

**Q：我是不是在"改 ROM"（像 FEBuilderGBA 那样打补丁）？**

**不是。** 打补丁是在已编译的二进制上找偏移量、改字节，脆弱且不可读。你走的是**从源码重建**路线：

- 你改的是 **C 源码和 JSON 数据**
- 框架用编译器**重新编译出整个 ROM**
- 改动之间**不会互相干扰**（不会因为改了 A 导致 B 的补丁地址错位）

代价是首次构建慢（约 15 分钟）、环境需要 WSL2。收益是**可维护性**完全不在一个量级。

### 1.5 为什么不直接用 `fireemblem8u` 反汇编项目？

因为你用不了它——它用 agbcc 编译，目标是**逐字节还原原版**。这条路线对改版的致命问题：

| 问题 | 后果 |
| --- | --- |
| 加一个新角色 → ROM 尺寸变化 → 所有地址偏移错位 | 必须手工修正大量硬编码地址 |
| 加中文 → agbcc 的工具链不支持 | 无法构建 |
| 没有数据层 | 改一个角色数值要手改 C 数组 |

而 `fireemblem8-expansion` 正是为解决这些问题而生的分支。它的 README 明确把 agbcc 路径称为"**archival side lane**"（档案侧车道）——**不再是主路径**。

### 1.6 两者能力对照

| 维度 | 原版《圣魔之光石》 | `fireemblem8-expansion` 框架 |
| --- | --- | --- |
| 编译器 | agbcc（2001） | 现代 `arm-none-eabi` GCC |
| 输出与原版关系 | 就是原版 | 不要求逐字节相同 |
| ROM 尺寸 | 16 MB | 默认 16 MB，本地化时 32 MB |
| 数据编辑 | 无源码，需工具 | JSON + 校验器 |
| 多语言 | 单语言 | 7 语言框架（含简中） |
| 扩展机制 | 无 | `expansion_mechanics.h` 注册式钩子 |
| 每次构建速度 | — | 约 15 分钟（首次，含工具链） |

## 3. 双车道架构：这是框架最核心的设计

**框架同时维护两条互不干扰的构建路径。** 理解这一点，很多困惑会自动消解。

| | **现代车道（modern）** | **档案车道（archival）** |
| --- | --- | --- |
| 命令 | `make`（裸跑即此） | `make legacy` |
| 编译器 | `arm-none-eabi-gcc` | `agbcc`（原版年代工具） |
| ABI | AAPCS | APCS-GNU |
| 链接脚本 | `linker/expansion.ld` | `ldscript.txt` |
| 输出路径 | `build/expansion-modern/release/aapcs/fireemblem8.gba` | `fireemblem8.gba`（仓库根） |
| 与原版关系 | **不要求**逐字节相同 | **要求**逐字节相同 |
| 配置指纹 | 有（嵌入 ROM） | 无（硬编码在 `rom_header.s`） |
| 多语言 | 支持（含简中） | 不支持 |
| 状态 | **支持的主路径** | 保活但**官方声明不维护** |
| 用途 | 你的改版开发 | 反汇编比对研究 |

### 3.1 为什么要有两条？

这不是为了复杂而复杂，是两个**目标不可调和**：

- **逐字节还原原版**要求：用原版同款编译器、同样的代码布局、同样的寄存器分配。这只能靠 agbcc。
- **可扩展的改版开发**要求：能加数据、能加代码、能加语言、能重排内存。这必须用现代 GCC。

框架的解法：**保留两条，主推现代，档案车道保活不删**。

### 3.2 对你的意义

**永远用现代车道。** 你不需要 `make legacy`，也不需要原版 ROM。

你的日常命令就是：

```bash
make
```

它会构建并**自动验证**现代车道的 release ROM。

### 3.3 一个重要陷阱

`docs/migration-from-decomp.md` 记录了历史包袱：

> 历史上，本仓库的默认构建、工具链和贡献指南都是"反汇编比对优先"（agbcc、逐字节相同）。**现在那已是明确不支持的侧车道。**

所以：**你在网上找到的关于 `fireemblem8u` 的教程，大部分是给档案车道写的**，直接照做会踩坑（比如指望 `make` 产出 `fireemblem8.gba`，或者以为需要 `baserom.gba`）。

## 4. 构建系统详解

### 4.1 构建流水线全貌

```
 ① 环境准备（一次性）
    WSL2 + Ubuntu → arm-none-eabi 工具链 → 宿主机工具（8 个）→ 子模块 mgfembp
                          ↓
 ② 配置（一次性）
    ./configure --with-enabled-locales=en,zh-Hans \
                --with-default-locale=zh-Hans \
                --with-rom-size=32M
    → 写出 config.autotools.mk（本地覆盖，不入库）
                          ↓
 ③ 数据生成
    src/data/*.json  ──[校验器]──→  build/generated/data/*.c
    texts/           ──[文本编码]──→  src/msg_data.c 等
                          ↓
 ④ 编译
    src/*.c（403 个）+ asm/*.s + generated/*.c
        ──[arm-none-eabi-gcc]──→  build/.../src/*.o
                          ↓
 ⑤ 链接
    所有 .o ──[linker/expansion.ld]──→ fireemblem8.elf
                          ↓
 ⑥ 后处理
    .elf ──[objcopy]──→ .gba → 修补 ROM 头（标题/产品码/校验和）
                          ↓
 ⑦ 验证（自动）
    boot-check：libmGBA 逐帧指纹比对（帧 0 / 60 / 120）
```

### 4.2 源文件是怎么被收集的（**改动代码必读**）

这是本轮调研最重要的一项发现。

`Makefile:131`：

```make
CFILES := $(wildcard $(C_SUBDIR)/*.c)
```

`modern.mk:359`：

```make
MODERN_ALL_C_SOURCES ?= $(wildcard src/*.c)
```

**结论：任何丢进 `src/` 的 `.c` 文件都会被自动编译链接进 ROM。不需要改 Makefile。**

这是"零侵入扩展"的基础。但有两个必须知道的配套事实：

**陷阱一：`wildcard` 在解析期展开，新增文件 make 感知不到。**

当你**新增**一个 `.c` 文件时，make 需要**重新解析 Makefile** 才能把它纳入列表。否则会出现最危险的情况：

> 文件躺在 `src/` 里，编译也"成功"，但**ROM 里根本没有它**。

**对策**：新增源文件后，先 `touch Makefile` 再 `make`。（我们的同步脚本会自动做这一步。）

**陷阱二：`Makefile:132-137` 有一份"排除清单"。**

```make
CFILES := $(filter-out src/action_semantics.c,$(CFILES))
CFILES := $(filter-out src/expansion_log.c,$(CFILES))
CFILES := $(filter-out src/expansion_autoplay.c,$(CFILES))
CFILES := $(filter-out src/expansion_chapter_objectives.c,$(CFILES))
CFILES := $(filter-out src/expansion_autoplay_strategies.c,$(CFILES))
CFILES := $(filter-out src/expansion_blue_phase_delegate.c,$(CFILES))
```

这些是**被故意排除**的源文件（原因各不相同：有的是纯测试用，有的是条件编译）。你新增文件时**避开这些名字**即可。

### 4.3 宿主机工具（host tools）

框架有 8 个"宿主机工具"——它们运行在**你的电脑上**（不是 GBA 上），负责把资源转换成 GBA 能用的格式：

| 工具 | 作用 |
| --- | --- |
| `aif2pcm` | 音频格式转换 |
| `bin2c` | 二进制 → C 数组 |
| `gbagfx` | GBA 图形格式转换（图集、调色板） |
| `jsonproc` | JSON 预处理 |
| `mid2agb` | MIDI → GBA 音乐格式 |
| `preproc` | 预处理器 |
| `scaninc` | 扫描 include 依赖 |
| `textencode` | 文本编码 |

**关键**：这些工具**必须预先构建**。框架的 Makefile **没有**把它们挂进正常依赖链——这是一个真实存在的坑（我们踩过，详见 `5.改版工程手册.md` §2.5）。

验证是否就绪：

```bash
for t in aif2pcm bin2c gbagfx jsonproc mid2agb preproc scaninc textencode; do
  [ -x "tools/$t/$t" ] && echo "OK  $t" || echo "MISS $t"
done
```

**必须 8 个全 OK。**

### 4.4 子模块：`mgfembp`

框架只有一个真子模块：

```ini
[submodule "mgfembp"]
	path = mgfembp
	url = https://github.com/StanHash/mgfembp.git
```

`git clone` **不加 `--recursive` 不会拉取**。正确的初始化：

```bash
git submodule update --init --recursive
```

> **不要**加 `--depth 1`。

### 4.5 配置的落盘位置

`./configure` 的结果写在 `config.autotools.mk`（**被 gitignore**）：

```make
MODERN_ROM_SIZE := 32M
EXPANSION_ENABLED_LOCALES := en,zh-Hans
EXPANSION_DEFAULT_LOCALE := zh-Hans
```

配置后**裸跑 `make`** 即产出中文版。

### 4.6 为什么中文本地化必须 32 MB？

这**不是容量问题**（实测中文字库只占 258.9 KB），而是框架的**架构强制**：

`scripts/modernize/expansion_config.py:404-411`：

```python
REAL_LOCALIZED_LOCALES = REAL_CJK_LOCALES + REAL_EU_LOCALES
# 若配置了任何真实本地化语言，且 ROM 尺寸不是 32M → 抛 ConfigError
```

设计原因是"**专属 upper-ROM locale bank**"——真实本地化语言需要一块独立的 ROM 上部区域来存放字库与目录数据。所以：

> **任何真实本地化语言（简中、日、法、德、西、意）都强制 32 MB。**

## 5. 数据平台：你 90% 的改动在这里

### 5.1 设计哲学

**数据与代码分离。** 你改数值、加角色、加道具，都在 JSON 里改，**不碰 C 代码**。

流程：

```
src/data/*.json
      │
      ├─[validate]─→ 校验（schema、引用完整性、容量上限）
      │
      ├─[generate]─→ build/generated/data/*.c  （类型化 C89）
      │
      └─[check]────→ 反查一致性
```

三个动词对应三个 make 目标（以角色为例）：

```bash
make generated-data-validate
make generated-data-generate
make generated-data-check
```

### 5.3 `fullCoverage` 机制（**新增角色必读**）

`characters.json` 开头：

```json
{
  "$schema": "fe8.characters.v1",
  "fullCoverage": true,
  "characters": [ ... ]
}
```

`scripts/generated_data/characters/schema.py:94-99` 说明它的语义：

> `fullCoverage: true` 开启 **1..256 密集覆盖校验**——全部 256 个角色槽位都必须有记录。

当前文件有 **94 条**记录，覆盖原版全部角色。

**这对《山河烬》意味着**：

- 你不能简单地"删掉原版角色、加自己的"——需要替换或复用槽位
- 加新角色时要考虑**槽位分配**：哪些原版角色被你的原创角色顶替
- 好消息：256 个槽位，原版只用了 94 个，**还有 162 个空位**可用

### 5.4 ID 空间双契约（`id_space.py`）

这是框架里一个**精妙但容易踩坑**的设计。

`scripts/generated_data/idspace.py` 是 ID 空间的**单一事实来源**，它定义两套契约：

| 契约 | 落盘位置 | 是否入库 | 特点 |
| --- | --- | --- | --- |
| **DEFAULT** | `include/id_space.h`、`reports/id_space_audit.*` | ✅ 入库 | 道具上限**恒为** `0xCD`（206 条） |
| **ACTIVE** | `build/generated/data/id_space_active.h` | ❌ 本地 | 随 `FE8_ITEM_ID_CAP` 变化 |

框架在编译期做静态断言：

```c
ITEM_ID_CONFIGURED_CAP == ITEM_ID_ACTIVE_CONFIGURED_CAP
```

**意义**：DEFAULT 是团队共享的"公开契约"，ACTIVE 是本次构建的"实际配置"。两者必须一致——否则编译失败。这防止了"改了配置但忘了更新文档"的问题。

### 5.5 逃生舱（`escape_hatch.py`）

某些数据无法用 JSON 表达（比如特别复杂的数组结构）。`CSymbolRefField` 允许你把 JSON 里的某个字段**绑定到手写的 C 符号**：

- JSON 里写一个符号引用
- 校验器做"**按构造的白名单**"检查（只允许预先声明的符号）
- 实际数据由你手写的 C 代码提供

这是"99% JSON + 1% 逃生"的平衡设计。

### 5.6 章节数据：按章挂载

`chapter_objectives.json` 当前是空数组：

```json
{ "chapters": [] }
```

章节数据是**每章一个独立 bundle 文件**（`chN_bundle.json`）。

每个 bundle 里有一个 `dependencies` 字段做**精确声明**。以下**全部**会导致校验失败：

- 依赖缺失 / 重复 / 过期 / 为空
- 超出容量
- 内部矛盾
- 循环依赖
- 无效区域
- 未知引用

还有 `externalReferences` 指向 `src/events/chN-eventscript.h`——**事件脚本的实际实现要写在 C 文件里**，JSON 只做引用声明。

### 5.7 存档格式与兼容纪元（**动存档前必读**）

框架把"存档格式"当作**公开契约**管理（判据见 `docs/public_api_policy.md`：存档文件是下游消费者之一）。

```c
/* include/expansion_config.h:162-163 */
#ifndef FE8_EXPANSION_SAVE_COMPAT_EPOCH
#define FE8_EXPANSION_SAVE_COMPAT_EPOCH 2
#endif
```

`include/save_format.h:34` 的要求：**任何改变存档布局的改动，都必须同时提升这个纪元号**；`:134` 说明它是写进存档并参与校验的字段。

**存档布局与这些常量耦合**（改一个等于改布局）：

| 常量 | 位置 | 影响 |
|---|---|---|
| `MENU_OVERRIDE_MAX = 0x10` | `include/uimenu.h:11` | `SUSPENDSAVE_SIZE_FORCENMENU = MENU_OVERRIDE_MAX * sizeof(u8)`（`include/sram-layout.h:51`） |
| `UNIT_SAVE_AMOUNT_*` / `GameSavePackedUnit.pid` | `src/bmsave.c` | 角色 ID 是 **8 位** → 这是"角色不能新增"的根因 |
| `jid` 7 位位域 | `src/bmsave.c:449-520` | 职业上限 `0x7F`，`0x80` **静默截断成 0** |
| `u8 ranks[8]` | `src/bmsave.c` | 武器类型只有 8 格 → **新武器类型加不了** |

**⚠️ 一个真实的观测（2026-09-25，本项目）**：实机遇到 `Menu_OnInit`（`src/uimenu.c:299`）野指针崩溃，**移开 `.sav` 后 60 秒不崩、恢复 `.sav` 即崩**。结论：**崩溃与存档强相关**。虽然尚在定位，但这条路线上有已知的结构性危险：

```c
/* src/bmsave.c：从存档读回"禁用菜单项"列表，再逐条安装覆盖 */
ReadSramFast(src->menuOverride, list, sizeof(list));
SetForceDisabledMenuItems(list);      /* → AddMenuOverride(...) */
```

而 `AddMenuOverride()`（`src/uimenu.c:719-728`）的查找循环**没有边界检查**：

```c
struct MenuItemOverride* it = sMenuOverrides;
while ((it->kind != 0) && !((it->kind == kind) && (it->cmdid == cmdid)))
    ++it;                    /* ← 表满且无匹配时会越过数组末尾 */
it->cmdid = cmdid; it->kind = kind; it->func = func;   /* ← 越界写 */
```

**⇒ 纪律**：动 `MENU_OVERRIDE_MAX`、`sMenuOverrides`、任何存档字段之前，**先读 `include/sram-layout.h` 与 `include/save_format.h`**。

## 6. C 代码层：游戏主体

### 6.1 规模与分布

| 类别 | 数量 |
| --- | --- |
| `src/*.c` | 403 |
| `include/*.h` | 172 |
| `src/*/` 子目录（data、events 等） | 多个 |

### 6.2 核心引擎：Proc 系统

框架最底层的运行时是 **Proc 系统**（`include/proc.h`、`src/proc.c`）：

- **协作式多任务调度器**，树状结构
- `struct Proc` = 实体
- `struct ProcCmd[]` = 脚本表
- 原语：`PROC_CALL` / `PROC_REPEAT` / `PROC_SLEEP` / `PROC_YIELD` / `PROC_START_CHILD_BLOCKING`

**理解 Proc 是理解 GBA 火纹代码的钥匙。** 游戏里每个"会等待用户输入的东西"——光标移动、菜单、战斗动画、过场——都是一个 Proc 节点。你没给它 `PROC_SLEEP`，它就会一帧跑一万次然后卡死。

#### 6.2.1 ☠️ 三个会"静默"咬人的 Proc 事实（外部研读报告第 3 章 + 本项目实测）

| # | 事实 | 后果 |
|---|---|---|
| 1 | **容量只有 64 槽**（`src/proc.c:13`），且 `AllocateProcess`（`src/proc.c:140-153`）**只做 `head++`，没有耗尽检查、没有断言** | 第 65 个 Proc **静默越界写内存**——不报错、不崩溃，症状会以**完全无关**的方式在别处显现 |
| 2 | **`PROC_REPEAT` 之后的脚本不再执行**：它把回调塞进 `idleCb` 后返假（`src/proc.c:498-504`），而 `idleCb` 非空时脚本推进被跳过（`:722-723`） | "每帧做点事 + 之后还想继续跑脚本"必须用 `PROC_YIELD`，不能用 `PROC_REPEAT` |
| 3 | **`Proc_End` 递归连杀整棵子树**（`src/proc.c:105-127`） | 杀父 Proc 会连带清掉子 Proc；反过来，忘了清子 Proc 就会泄漏槽位 |

> **对本项目的直接影响**：`docs/3` 的战斗机制、`docs/8` 的法术特效都会新增 Proc。**"每个单位起一个 Proc"这种写法在 12 人以上战场上极可能撞 64 槽上限**，而且撞了也不报错。写之前先数清当前树规模。

### 6.3 扩展机制层：`ExpansionMechanicsRegister()`

这是框架官方给你的**机制扩展入口**，定义在 `include/expansion_mechanics.h`。

用途：**修改战斗计算**。你注册一个回调，它在战斗数值计算时被调用，可以改数值。

容量上限：`EXPANSION_MECHANICS_MAX = 8` 个注册回调。

#### 6.3.1 apply 顺序陷阱（**极其重要**）

调研中发现的真实坑：

`BattleGenerate()` 的计算顺序是：

```
1. compute 攻击者 → 触发 apply #1（subject = 攻击者，opponent = 防御者）
2. compute 防御者 → 触发 apply #2（subject = 防御者，opponent = 攻击者）
3. ComputeBattleUnitEffectiveStats()  ← 在两者之后！
```

**问题**：在 apply #1 时，防御者的战斗数值**还没算出来**。

如果你在 apply #1 里读 `context->opponent->battleDefense`，读到的是**未初始化数据**——这是一个真 bug，但编译不报错、运行不崩溃，只是数值诡异。

**安全输入清单**：

| 可以安全读 | 不可以读 |
| --- | --- |
| subject 自身的战斗数值 | `opponent->battleAttack` |
| `opponent->unit` 的底层数据（职业/等级/状态/位置/HP） | `opponent->battleDefense` |
| config 上下文 | `opponent->battleHitRate` |
| | `opponent->` 任何 `battle*` 字段 |

#### 6.3.2 ☠️ 覆盖边界（**比容量上限更容易踩空**）

外部研读报告核实的关键事实：

| 约束 | 事实 | 出处 |
|---|---|---|
| **只覆盖一条路径** | `ExpansionMechanicsApplyBattleStats` 的**唯一调用点**是 `src/bmbattle.c:513-522`，即只覆盖 `ComputeBattleUnitStats` | 报告第 6 章 |
| **物品/杖不算** | **物品与杖的结算走 `BattleInitItemEffect`（`src/bmbattle.c:2145,2171`），完全不经过这个钩子** | 报告第 6 章 |
| **明文禁改** | 框架文档明确禁止直接改 `ComputeBattleUnitStats`（`docs/starter_features.md:191-195`） | 同上 |
| **钩子是"加法式"** | 只能在既有结算结果上再加一项，**覆盖不到公式本体**（改"伤害公式长什么样"必须落 L3 直改 `BattleUnwind`，`src/bmbattle.c:765-791`） | 报告第 3/6 章 |
| 其它 | 注册回调期间再注册会被拒（`ERR_REENTRANT`）；回调收**可变 subject** + **只读 opponent/config** | 本项目实测 |

> **⚠️ 对本项目的直接含义**：《山河烬》的「符箓三宝」「医药」若做成**道具/杖**，则**官方机制钩子完全吃不到**——
> 想让它们参与数值结算，只有 L3 直改 `src/bmbattle.c`（并接受回归风险）。
> 这是 `docs/3` §2.4「三才法器」/ §2.5「医药与兽灵」在设计上必须先确认的一件事。
>
> **判断口诀**（报告原文提炼）：**要"多一条加成"→ L2 够；要"换一套算法"→ 直接准备 L3。**

### 6.4 三条接入通道（**你的新代码往哪放**）

| 通道 | 位置 | 覆盖场景 | 山河烬用得多吗 |
| --- | --- | --- | --- |
| **① 内容层** | `src/data/*.json` | 数据：角色/职业/道具/武器三角/章节 | ★★★★★ 90% |
| **② 机制层** | `ExpansionMechanicsRegister()` | 战斗数值修改 | ★★★☆☆ 神器/凶相 |
| **③ 引擎层** | 直接改 `src/*.c`、`include/*.h` | 改战斗流程、加新系统 | ★★☆☆☆ 谨慎使用 |

**原则：能用①就用①，能用②就用②，③是最后手段。**

原因：① 和 ② 有校验器保护，③ 改错了直接崩溃或者更糟——静默产生错误行为。

### 6.5 命名约定（**避坑**）

`src/` 下已有 **21 个** `expansion_*.c` 文件。

**如果你新增的文件与上游同名，会静默替换上游实现**——编译成功，行为诡异。这是最危险的"覆盖"形态。

**约定：山河烬的原创 C 文件统一加 `shanhe_` 前缀。** 例如：

- `src/shanhe_sacred_relics.c`（神器系统）
- `src/shanhe_four_ominous.c`（凶相双血条）
- `src/shanhe_dual_triangle.c`（双环武器三角）

## 7. 本地化层：中文是怎么进来

### 7.1 架构

```
texts/expansion/registry.json        ExpansionMsgId 的稳定来源
texts/expansion/catalog.en.json      英文字符串
texts/expansion/catalog.zh-Hans.json 简体中文字符串
                │
                ├─[textencode 等工具]─→ src/msg_data.c、字库
                │
                └─→ ROM 中的（压缩后）本地化 blob
```

关键设计：

- **`ExpansionMsgId` 是只追加的**（append-only）——ID 一旦分配就不再变，保证存档兼容
- **`ExpansionLocaleId` 预留稳定槽位**
- 运行时用 **EWRAM 解析缓存** + **校验和的语言偏好**（存在存档元数据里）
- **独立于原版的 `MSG_*` / `GetLang()` 体系**——这是刻意的，避免污染原版逻辑

### 7.2 支持的 7 种语言

English（默认）、Japanese、**Simplified Chinese**、French、German、Spanish、Italian。

另有 `qps-ploc` 伪语言（用于 UI 测试，不是翻译）。

### 7.3 中文字库实测数据（已由本项目验证）

| 资源 | ROM 地址 | 大小 | 内容 |

| `gLocalizedFontZhHansSystemCodepoints` | `0x09000000` | `0x016D0` | 1,460 字形 |
| `gLocalizedFontZhHansSystemBitmaps` | `0x09001C84` | `0x16D00` | 91.2 KB |

## 8. 验证体系：怎么证明"我改的生效了"

### 8.1 三层验证

| 层 | 手段 | 能发现什么 |
| --- | --- | --- |
| **数据层** | `make generated-data-validate` / `check` | JSON 错误、引用断裂、容量超限 |
| **构建层** | 编译成功 + 链接断言 | 类型错误、符号缺失、内存溢出 |
| **运行层** | `boot-check`（libmGBA 指纹） | 启动崩溃、行为漂移 |

### 8.2 boot-check 机制

`tools/gba-playtest/` 用 libmGBA **逐帧重放**输入场景，比对**帧缓冲与 RAM 检查点指纹**：

```
fingerprint verified: policy=behavior scenario=boot checkpoints=3
```

- 检查帧：**0 / 60 / 120**
- `--policy behavior`：**行为策略**，不要求字节相同（因为现代车道本就不逐字节还原）
- 捕获输出总是记录 ROM 溯源（SHA-1、尺寸、标题、产品码）

完整的场景套件涵盖：boot、title、new-game、chapter load、combat、suspend/resume、save/load、debugtools hub。

### 8.3 其它 gate

| Gate | 作用 |
| --- | --- |
| `expansion-modern-boot-check` | 启动行为验证 |
| `expansion-modern-linker-check` | 在 boot 基础上加：预算漂移、shift、overlay 审计 |
| `make localization-test` | 本地化目录测试 |
| `make generated-data-check` | 数据反查 |

### 8.4 对你的实践的启示

改完内容后，最低限度的验证顺序：

```bash
make generated-data-check      # 数据层
make                           # 构建 + boot-check
```

再配上 mGBA 实机看一眼（`5.改版工程手册.md` §8.1-8.2）。

**特别注意**：如果你的改动"编译过了但游戏里没变化"，检查第一件事是——

> **新增的 `.c` 文件是否被 make 感知到？**（见 §4.2 陷阱一）

## 10. 关键发现与陷阱速查

### 10.1 本轮调研的四个重要发现

1. **`src/*.c` 自动编译**（wildcard）→ 零侵入扩展可行，不需要改 Makefile
2. **但新增文件需 `touch Makefile` 强制重解析** → 否则静默不生效
3. **`fullCoverage: true` 开启 256 槽位密集校验** → 加角色需考虑槽位分配（剩 162 空位）
4. **`ExpansionMechanicsRegister()` 有 apply 顺序陷阱** → apply #1 时读不到 opponent 的战斗数值

### 10.2 陷阱清单

| # | 陷阱 | 后果 | 对策 |
| --- | --- | --- | --- |
| 1 | 宿主机工具未预构建 | 构建报假错（文件名是猜的） | 先跑 `tools/shanhe.sh` §6 |
| 2 | 子模块未拉取 | `mgfembp/*` 缺失 | `git submodule update --init --recursive` |
| 3 | 新增 `.c` 未触发重解析 | **文件在，ROM 里没有** | `touch Makefile` |
| 4 | 与 `expansion_*.c` 同名 | 静默替换上游 | 用 `shanhe_` 前缀 |
| 5 | 用了排除清单里的文件名 | 不编译 | 避开那 6 个名字 |
| 6 | 机制回调读 opponent 战斗数值 | 读到未初始化数据 | 只读 `opponent->unit` |
| 7 | 忘了 32M 要求 | configure 报错 | 本地化必须 `--with-rom-size=32M` |
| 8 | 在框架仓库跑 `git clean` | 删掉未追踪的原创源文件 | **绝不要跑** |
| 9 | **`make clean` / `clean_fast`** | `CLEAN_DIRS` 含整个 modern 构建根并对其 `rm -rf`（`modern.mk:837`、`Makefile:491`）→ **连构建好的 ROM 一起删**；且 locale profile 根是**同级目录**，`expansion-modern-clean` 清不到，反复构建吃几 GB | 构建成功后**先把 ROM 复制到别处**（`shanhe-build.sh` 第 5b 步已自动导出）；清理时用 `expansion-modern-clean` 而非 `make clean` |

## 11. 对《山河烬》的直接结论

1. **技术底座是可靠的。** 403 个 C 文件、完整数据平台、三层验证、官方中文本地化——这不是玩具框架。
2. **你的战场在 JSON 和文本，不在 C。** 90% 的工作量在 `src/data/*.json` 和 `texts/`。
3. **零侵入扩展已确认可行。** 原创 C 代码用 `shanhe_` 前缀放 `src/`，配合 `touch Makefile`。
4. **但 `fullCoverage` 要求你正面处理原版角色。** 94 个槽位占用中，你需要决定替换策略。
5. **武器三角双环改造是纯数据操作。** `weapontriangle.json` 已有数据驱动机制，改 JSON 即可——这是本轮调研的一个高价值发现。
6. **验证不能省。** 尤其"改了没生效"这类静默失败，必须靠 boot-check + mGBA 实机确认。
