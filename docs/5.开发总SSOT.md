## 1. 核心决策：FEBuilder 主链路

### 1.1 决策记录

**2026-09-30 拍板**：数据表落 ROM 的链路，从「Plan B 内容外置（自定义 JSON → 生成 C → 编译）」**切换为「FEBuilder 主链路」**（官方布局 baserom + `--import-data` 直接写 ROM）。

**原因**：
- 用户希望**按 FE/FEBuilder 的原生格式和命名**规划数据表，以便**直接导入 FEBuilder**（用 GUI 可视化核对、用 `--lint` 校验）。
- 自定义 schema（`classes.json` 里的 `"promotion": "CLASS_EIRIKA_MASTER_LORD"`、`nameTextId: 703`）与 FEBuilder 的导入格式**不兼容**，无法直接导入。

### 1.2 两条链路的本质区别（务必分清）

| | Plan B 外置（旧） | FEBuilder 主链路（新） |
|---|---|---|
| 载体 ROM | 反编译重建（`shanhe-cn-32m.gba`） | **官方布局 baserom**（16MB） |
| 数据格式 | 自定义 JSON schema（camelCase + 文本ID + 符号枚举） | FEBuilder JSON（FE 原生字段名 + hex 字符串值） |
| 字段例 | `"promotion": "CLASS_EIRIKA_MASTER_LORD"` | `"PromotionClass": "0x03"` |
| 落 ROM 方式 | `shanhe-build.sh` → 生成 C → `make` | `--import-data --table=X --in=X.json` |
| 校验方式 | 生成物 SHA1 比对 | `--lint` + `--data-roundtrip` |

## 2. FEBuilder 数据导入格式（权威规范）

### 2.1 导入命令

```bash
FEBuilderGBA.CLI --import-data --rom=<baserom副本.gba> --table=<表名> --in=<数据.json>
# --format=json 可省略，.json 扩展名自动识别
```

- CLI 路径：`D:\workbuddy\FEBuilderGBA\FEBuilderGBA.CLI\bin\Release\net10.0\FEBuilderGBA.CLI.exe`
- 40 张表名见 §3 速查表。

### 2.2 JSON 格式契约（严格）

```json
[
  { "Index": "0x01", "ClassID": "0x0E", "BaseHP": "0x12", "SwordRank": "0x1F" },
  { "Index": "0x02", "ClassID": "0x58", "BaseHP": "0x13", "SwordRank": "0x00" }
]
```

**四条铁律（违反即导入失败，ROM 不动）：**

1. **根是数组**，每行一个对象。
2. **键 = 字段名**（FE 原生命名，见 §3 各表字段清单）。`Index` 是行标识键，值可以是 `"0x01"` 或 `"0x01 角色名"`（hex + 空格 + 标签）。
3. **值 = hex 字符串**，`"0x"` 前缀（或 `$` 前缀 / 纯十进制），**永远不是 JSON 数字/布尔**。
4. **字段名拼错、值溢出、Index 越界、重复行 → 全部拒绝**，且 ROM 逐字节不变（可放心重试）。

### 2.3 正确性门（导入后必跑）

```bash
# 结构/指针/文本ID 校验（不校验玩法平衡）
FEBuilderGBA.CLI --lint --rom=<baserom副本.gba>
# 读写稳定性（临时副本往返对比）
FEBuilderGBA.CLI --data-roundtrip --rom=<baserom副本.gba> --table=units
```

> 注意：这两个门**只保证数据没写坏、指针没悬空**，**不判断数值是否平衡**。数值合理性靠 `docs/3` 的设计值兜底。

## 4. 制作顺序与依赖（★ 本文档核心）

数据表之间通过**外键引用**关联，制作顺序遵循「**被引用方先做**」。三层依赖：

```
第 1 层（无依赖，先做）    第 2 层（依赖第 1 层）        第 3 层（依赖第 2 层）
┌─────────────────┐        ┌─────────────────┐        ┌─────────────────┐
│ ① classes 职业   │        │ ③ units 角色     │        │ ⑤ support 三表   │
│ ② items 道具/武器 │───►    │ ④ weapon_triangle │───►    │ ⑥ map_settings   │
└─────────────────┘        └─────────────────┘        └─────────────────┘
```

### 4.1 依赖关系明细（外键 = 依赖）

| 序号 | 表 | 依赖（外键） | 依赖谁 | 说明 |
|---|---|---|---|---|
| ① | `classes` | 无 | — | 根之一，`PromotionClass` 自引用 |
| ② | `items` | 无 | — | 根之一 |
| ③ | `units` | `ClassID` → classes；`*Rank` 门槛 → items | ①② | 角色引用职业 + 武器 |
| ④ | `item_weapon_triangle` | `WeaponType1/2` → items.WeaponType | ② | 克制引用武器系 |
| ⑤ | `support_*` | `UnitID` → units | ③ | 支援引用角色 |
| ⑥ | `map_settings` | `UnitID` → units；`TerrainTableID` → 地形 | ③ | 章节引用角色 |

### 4.2 关键结论

1. **「数值设计」可以并行**：`docs/3` 里的职业数值、武器数值、角色数值是**设计层**，可同时准备（数值本身无外键）。
2. **「导入 FEBuilder」必须按层序**：先导 `classes` + `items`，再导 `units`（此时才能填 `ClassID` 指向已存在的职业），最后导 `support`/`map_settings`。
3. **先填 Demo 七人**：`docs/3 §4.2/§5.1` 已定 Demo 七角色 + 七职业低阶数值，这是内容层的第一批导入目标（对应 M4 交付物②）。

## 5. 数值映射规则（docs/3 设计值 → FE 字段）

### 5.1 设计九维 → FE 字段

《山河烬》面板九维 **HP/力/魔/技/速/运/防/魔防/体格** 映射到 FE 字段：

| 设计维度 | FE 字段（units/classes） | 说明 |
|---|---|---|
| HP | `BaseHP` / `GrowthHP` / `MaxHP` | 直映射 |
| 力 | `BasePow` / `GrowthPow` / `MaxPow` | **力/魔合并**为 Pow（火纹传统） |
| 魔 | （同上 `Pow`） | 魔法系也走 `Pow`，靠 `WeaponType` 区分物理/魔法 |
| 技 | `BaseSkl` / `GrowthSkl` / `MaxSkl` | Skill |
| 速 | `BaseSpd` / `GrowthSpd` / `MaxSpd` | Speed |
| 运 | `BaseLck` / `GrowthLck` | Luck（无 Max） |
| 防 | `BaseDef` / `GrowthDef` / `MaxDef` | Defense |
| 魔防 | `BaseRes` / `GrowthRes` / `MaxRes` | Resistance |
| 体格 | `BaseCon` / `MaxCon` | Constitution |
| 移动 | `BaseMov`（仅 classes） | 由职业决定，角色无此字段 |

> ⚠️ **「力/魔」在设计文档里是两维，但 FE 物理上只有一个 `Pow` 字段**。魔法攻击用 `Pow`（魔）vs `Res`（魔防），物理攻击用 `Pow`（力）vs `Def`（防），靠 `WeaponType` 判定走哪套。**填表时力/魔只能填一个值**，法系角色（婉莹/温子墨/阿蘅/云虚）的 `BasePow` 填「魔」值。

### 5.2 成长率映射

- `docs/3 §4.2` 的成长率 `70/45/10/50/55/40/30/15` = HP/力/魔/技/速/运/防/魔防。
- 因 FE 力魔合并，`GrowthPow` 只取一个值（物理角色取「力」，法系角色取「魔」）。
- 最终成长率 = `units.Growth*`（个人）+ `classes.Growth*`（职业，**仅敌方/自动升级生效**，玩家单位只看个人）。

### 5.3 武器熟练度映射

- `docs/3 §2.8` 的 E/D/C/B/A/S 门槛 → `units.*Rank` / `items.WeaponRank`。
- 8 系：`SwordRank/LanceRank/AxeRank/BowRank/StaffRank/AnimaRank/LightRank/DarkRank`。
- 《山河烬》武器系 → FE ITYPE 映射（见 `docs/9 §4.2`）：
  - 剑/刀/短刀 → `ITYPE_SWORD`；锤 → `ITYPE_AXE`；枪 → `ITYPE_LANCE`
  - 弓/弩 → `ITYPE_BOW`；法器·天道 → `ITYPE_ANIMA`；地脉 → `ITYPE_DARK`；人和 → `ITYPE_LIGHT`

## 6. 工作流约定

### 6.1 每张表的制作闭环

```
1. 在 docs/3 定好设计值
2. 按本文档 §3 字段清单 + §5 映射规则，写 <表名>.json（FE 原生字段名 + hex 值）
3. --import-data 导入官方 baserom 副本
4. --lint + --data-roundtrip 校验
5. 把 <表名>.json 提交 git（数据表是资产，进版本管理）
```

### 6.2 文件存放位置

- **FEBuilder 格式的 JSON** 存 `content/data/febuilder/<表名>.json`（新目录）。
- **Plan B 自定义 schema 的 JSON 已全部清理**（2026-09-30，见 §1.3a）。`content/data/` 下现在只有 `.gitkeep` 占位符，等待 FEBuilder 格式的 JSON 从零填入。

> 旧 Plan B 数据（`characters.json`/`classes.json`/`weapontriangle.json`/`items_expansion.json` + `shanhe_*_units.json` + `content/src/` 的 3 个 C）已删除，git tag `before-planb-content-cleanup-20260930` 保留可回溯锚点。

### 6.3 载体 ROM 副本管理

- 官方 baserom 是**只读基准**，每次导入前 `cp` 一份到工作目录，导入结果单独命名（如 `shanhe-data-v1.gba`）。
- **绝不直接改原始 baserom**，保留可回溯的干净副本。
