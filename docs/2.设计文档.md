## 0. 目标与范围

- **目标**：一部约 20 章完整故事线、单线推进的原创世界观 SRPG，玩法与观感致敬 GBA 火焰纹章。**画风按 100% 还原原版为目标**——这是本项目的核心诉求，也是技术路线选择的唯一决定性因素。
- **游戏名**：**《山河烬》**（已拍板；同名检索无商业游戏冲突）。**英文名（暂定）**：*Realm in Ashes*。
- **成功标准**：完整可通关 20 章；玩家（自己 + 同好）评价"和原版火纹一个味"。
- **发布**：**免费分享给同好，不卖钱**；分发形式 = **补丁（.ups/.bps）+ 打补丁说明**，玩家用 mGBA / RetroArch / 安卓模拟器 / 开源掌机游玩。
- **v1 明确不做**：联网对战、商业化、多语言（先中文）、多周目差分、移动端原生 App。
- **体量红线（待拍板）**：20 章为目标体量；**12~15 章为可接受缩水线**（砍掉部分中幕章节、外传优先保留），在 P3 demo 决策门时按实际产出速度再评估——solo 开发防止"全或无"烂尾。

## 2. 核心玩法

- **网格**：地图格 16×16 像素，可视 15×10 格；地形移动力消耗——**原版规格，无需设计**。
- **回合**：玩家回合 / 敌方回合——**原版规则**。
- **战斗公式**：以 **`3.游戏数值设定.md` 第 1 节为唯一来源**。实现落位于原版战斗代码（`src/`，见 §12）；2RN 判定、追击阈值均为原版行为，**改造时须显式决定"是否保留原版"**（见 §11 改造清单）。
- **克制关系（本项目原创，需改写原版）**：
  - **兵刃三环**：枪 → 刀 → 锤 → 枪；**剑不入环**（中立生态位，主角/剑客系）；
  - **三才法环**：天克地、地克人、人克天；
  - 弓、弩在环外；克制标签只对攻击类法术生效。
  - **实现方式**：原版武器三角为"剑→斧→枪"单一环，本项目需要**双环 + 环外特例**——这是必须改代码的第一处（`src/data/` 有武器三角机制表，配合 `include/expansion_mechanics.h`）。
- **敌方 AI**：原版已有完整的 AI 框架（进攻/驻守/逃跑/治疗/盗贼开箱）。
  - v1：沿用原版 AI + 调整权重（可击杀 > 伤害期望 > 命中率）；
  - v2（P4）：细化护送目标保护权重、凶相专属行为。
- **战场信息 UX**：战斗预测面板 / 危险范围 / 单位详情 —— **原版全部已有**，仅需：① 确认中文文本渲染正确；② 确认三环克制修正能显示在预测面板中。
- **悔棋（可选增强）**：原版无"回溯"，但有**每回合自动存档**（`SUSPEND`）。方案二选一：① 依赖模拟器即时存档（推荐，零成本）；② 在机制钩子中实现快照回溯（成本中等，收益低）。
- **经验与成长**：个人成长率 + 职业成长加成——**原版系统**。随机/固定成长切换通过机制钩子实现。
- **转职**：`classes.json` 的 `base`/`max`/`growth`/`promotionGain` 字段原生支持 1~3 阶与分支。
- **神器系统**：9 件神器（圣皇铸鼎余料）。规则与数值见数值文档第 3 节；特效 = 专属配色 + 粒子层。**原版道具上限为 `0xCE`，扩展道具需 `--enable-mechanics-hooks` + 提升 item cap。**
- **说得系统**：原版已有"说得"指令（`Talk`），复用即可；第 3 章郡丞卫队长为首个用例。
- **支援与感情线**：义理值四档（陌路→相识→相知→生死之交）→ 映射到原版支援 C/B/A；战斗加成见数值文档第 8 节。**`supports.json` 要求支援关系必须双向**（框架强制校验）。
- **物品栏与仓库**：**原版内置**（5 格 + 运输队 100 格）。
- **出击与整备**：**原版内置**（整备界面选人/换装/商店/查看）。
- **商店/装备/耐久**：**原版系统**；神器走"黯淡 + 龙髓/铁匠铺"独立规则（需新增）。
- **存档**：**原版系统**（3 槽 + 中断档）；框架已扩展 `ExpansionUserPrefs`（0x0C 字节 SRAM 记录）用于语言等偏好。

## 3. 章节结构

- **五幕 20 章**（结构详见世界观圣经第 4 节）：一·故乡失火（序~4）→ 二·帝都迷局（5~7）→ 三·北地真相（8~12）→ 四·会盟天下（13~16）→ 五·归墟决战（17~20）+ 外传 2 个（白鹤观旧事 / 幽都判官）。
- 每章流程：开场剧情（史书体旁白）→ 战前情报 + 整备 → 战斗 → 战后剧情。**原版事件脚本框架原生支持此流程。**
- 胜利条件类型：全灭 / 护送 / 防守 N 回合 / 占旗压制 / 限时 / 攻城 / BOSS 击退。
  - **框架原生支持的目标类型**（`chapter_objectives.json`）：`reach_area`、`defeat_group`、`protect`、`hold_until_turn`、`event_flag`；
  - **需扩展的**：占旗压制、限时、攻城 —— 可用 `event_flag` + 事件脚本组合实现；
  - 每章上限 8 个 objectives、8 个 AI 组、每组最多 16 个成员（**框架硬约束**）。
- **事件触发器**：**直接用原版事件脚本体系**（`eventscripts.json` / `eventlists.json` + Event Assembler 语法）。原版已支持回合数、区域进入、单位死亡、村庄访问、说得、战斗对话等全部触发器，**无需自研 EventRunner**。
- **Demo = 序章~第 4 章（5 关）**，完整跑通全部系统后作为决策门验收；关卡配置见规划手册 §4 M4 的门禁项（关卡表待产出，见该手册 D-6）。
- **教程策略**：序章强制教学（移动/攻击/克制/护送）；新机制首次出现弹提示卡。**原版无此机制，需新增**（用事件脚本 + 消息文本实现，成本低）。
- **章节数据落位**：每章一个 `src/data/chN_*.json` 捆绑（`units` / `shops` / `traps` / `eventscripts` / `eventlists` / `bundle`），见 §12。

### 5.1 中文字库容量（**v0.7 实测完成，风险降级**）

**实测结论（2026-09-25，从 ELF 符号表量取，详见 `5.改版工程手册.md` §3.5）**：

| 指标 | 实测值 |
|---|---|
| 字形总数 | **3,842**（System 1,460 + Talk 2,382） |
| 字库总计（码表+宽度+位图） | **258.9 KB ≈ 0.25 MB** |
| 文本目录压缩块 | 486.5 KB |
| 32M ROM 空闲（0xFF 填充） | **约 14.66 MB（45.81%）** |
| 单字形成本 | 约 **62 字节** |

**v0.6 的假设被修正**：原文称"框架的 CJK 字体页按字频取前 150 个标量（两页 75 格）——这是示例规模，真实项目 20 章剧本文本量远超此数"。实测表明**这已不成立**：框架的字体页是**自动确定性生成**的（按 `texts/locales/zh-Hans/` 实际用字统计字频），当前空目录状态下已生成 3,842 字形，**不是 150 个的示例规模**。

**空间层面完全无压力**：中文全套只吃 0.25 MB 字库 + 0.49 MB 文本。即便 20 章全量剧本用字翻三倍（约 1.2 万字形），字库也仅约 0.75 MB，32M ROM 绰绰有余。

**因此**：
- ❌ 原"P0 最高优先级技术风险：字库容量不足"**撤销**；
- ✅ 保留的硬约束只有一条：**中文版必须 `MODERN_ROM_SIZE=32M`**。但根因**不是容量不足**，而是框架把本地化资源放在"专属 upper-ROM locale bank"的**架构分层**要求（源码见 `scripts/modernize/expansion_config.py:404-411`）。**不要试图用 16M 省事，configure 会直接拒绝**。
- ⬜ **仍待人工验证的一项**：中文文本在**实际渲染**时是否溢出/断行错误/出现豆腐块（缺字方框）。数值上无压力 ≠ 渲染正确，这需要 mGBA 实机过目。若出现豆腐块 → 扩充 `texts/locales/zh-Hans/` 字符集后重跑 `make localization-generate`，扩字成本仅约 62 字节/字。

> **方法论教训**：本条的误判源于**只看代码注释与函数名就推断规模，没有实测**。`docs/5.改版工程手册.md` §2.5 的「报错信息可信度分级」表同样教训——凡涉及容量/性能的判断，必须量到真实数字才算数。

## 6. 技术架构（FE8 扩展框架）

- **基底**：`laqieer/fireemblem8-expansion`（基于 fireemblem8u 反汇编，MIT 风格开源），以现代 `arm-none-eabi` GCC 工具链从源码构建 ROM。
- **不需要原版 ROM 即可构建**（原版 ROM 仅用于反汇编比对 `asmdiff.sh`）。
- **开发环境（Windows 用户必读）**：
  - 官方自动安装脚本仅支持 **Ubuntu / WSL / Arch / macOS**；
  - **WSL2 (Ubuntu) 是 Windows 下的推荐且事实唯一路径**；
  - 仓库须放在 WSL 文件系统内（`~/`），**不要放 `/mnt/d/`**（跨文件系统会极慢）；

  - ⚠️ **构建前必须预构建 `tools/` 下 8 个宿主机工具**——框架 Makefile 未把它们的构建规则挂进依赖链，缺失时报错会指向**根本不存在的文件**（详见 `5.改版工程手册.md` §2.5 专栏）。
- **构建产物**：`build/expansion-modern/release/aapcs/fireemblem8.gba`；另有 `.elf`（带调试符号）、`.map`（链接器映射）。**已在 2026-09-25 实机产出 16M 英文版与 32M 中文版，boot-check 双通过。**
- **数据驱动层**（**这是日常改内容的主战场**）：
  - 所有内容用 JSON 写在 `src/data/` 下；
  - 三个统一动词：`validate`（校验）/ `generate`（生成 C89）/ `check`（漂移门禁，CI 用）；

  - **绝不手工编辑 `build/generated/data/` 下的生成代码**。
- **代码层**：`src/` 下的 C 与 ARM 汇编；`include/expansion_mechanics.h` 提供带容量约束的战斗属性注册表（回调收到可变攻击者 + 只读防御者上下文）。

## 12. 代码与文档落位映射

> 给未来的自己：改什么、去哪里改。框架路径以 `fireemblem8-expansion` 仓库为准。

### 12.1 三条接入通道（**核心机制，先读这个**）

框架**没有**"用户侧独立目录"机制——不存在 `FE8_PROJECT_DIR` 之类的变量，也没有内容覆盖层。你的东西必须**按框架既有的扩展点接进去**。好消息是它预留了三个通道，按改动风险递增：

| 层 | 通道 | 适合放什么 | 风险 |
|---|---|---|---|
| **内容层** | `src/data/*.json` + 数据管线 | 角色、职业、武器、关卡、事件、支援、商店、目标。**90% 的改动在这里，不用写一行 C** | 低 |
| **机制层** | `ExpansionMechanicsRegister()`（`include/expansion_mechanics.h`） | 战斗数值类原创系统：兵刃三环、三才法环、神器加成、凶相相关结算 | 中 |
| **引擎层** | 直接改 `src/*.c`、`asm/` | 钩子表达不了的结构性改造：双血条**显示**、新菜单、对话框改造 | 高（须回归测试） |

**选择原则**：能用内容层解决就不用机制层，能用机制层解决就不动引擎层。因为每往下一层，破坏原版行为的面就大一圈。

### 12.2 内容层：日常主战场

所有内容用 JSON 写在 `src/data/` 下，走三个统一动词：

```bash
python3 -m scripts.generated_data validate --table characters   # 校验，报 file:line:column
python3 -m scripts.generated_data generate --table characters   # 生成 C89 到 build/generated/data/
python3 -m scripts.generated_data check    --table characters   # 漂移门禁，CI 用
```

或全平台 Make 目标：`make generated-data-validate / -generate / -check`。

**铁律**：
- **绝不手工编辑 `build/generated/data/` 下的生成代码**——那是产物，会被重新生成覆盖。
- 跨表引用一律用符号（`CHARACTER_*` / `CLASS_*` / `ITEM_*` / `MSG_*` / `EVFLAG_*`），悬空引用立即报错。
- `characters` 是**硬性 256 槽**数组，超了 manifest 失败。加原创角色前先看 §12.4 的 ID 空间规则。

**逃生舱**：当某个字段必须指向**手写 C**（回调指针、共享常量/表）而非生成器能造的值时，用 `CSymbolRefField` 把 schema 字段绑定到一个具体头文件——校验器会做"按构造的白名单"检查（符号必须在该头文件中声明），生成器把名字当作裸 C token 输出。实现见 `scripts/generated_data/escape_hatch.py`。**这是把你的手写代码接进数据层的官方通道。**

### 12.3 机制层：原创战斗系统挂这里

`include/expansion_mechanics.h` 提供的是一个**固定容量（8 个）、强类型**的战斗数值钩子注册表。它的设计意图就是"让你扩展战斗数值，而**不用手改 `src/bmbattle.c`**"。

挂载点：`ComputeBattleUnitStats()` 在**每个战斗单位的所有原版基础数值算完之后、生效值计算之前**，调用一次 `ExpansionMechanicsApplyBattleStats()`。

```c
typedef void (*ExpansionMechanicsBattleStatFunc)(
    struct BattleUnit* subject,                          /* 可变：可改已算出的战斗数值 */
    const struct ExpansionMechanicsContext* context);    /* 只读：含 opponent 与 battleConfig */
```

⚠️ **最容易踩的坑：apply 顺序**。`BattleGenerate()` 是**先后**算两个战斗者的：

```
ComputeBattleUnitStats(&gBattleActor,  &gBattleTarget);   /* apply #1 */
ComputeBattleUnitStats(&gBattleTarget, &gBattleActor);    /* apply #2 */
ComputeBattleUnitEffectiveStats(...);                     /* 两者都在此之后 */
```

所以在 **apply #1 时，`context->opponent`（防御方）的战斗数值还没算**——它的 `battleAttack`/`battleDefense`/`battleHitRate` 等仍是上一轮或初始化的残留值，**读它就是真 bug**。

**安全输入**：subject 自己已算出的战斗数值；opponent 的**底层 unit 数据**（职业、等级、状态、位置、当前/最大 HP）。
**不安全输入**：任何 `opponent->battle*` 字段。

→ 所以兵刃三环/三才法环这类**需要双方克制关系**的机制，**不能**写在这个 seam 上（它读不到对方的最终数值）。两条出路：
1. 只依赖双方的**底层 unit 数据**推断（例如读武器类型、职业属性，这些在 apply #1 就稳定）；
2. 若确实需要双方最终战斗数值，**属于更晚的 seam**——不要靠缓存状态绕过顺序（注册与 apply 顺序是确定的，但配对不可重入，apply 期间注册会被 `EXPANSION_MECHANICS_ERR_REENTRANT` 拒绝）。

**启用方式**：

```bash
./configure --enable-mechanics-hooks          # 挂上注册表
make
# 需要 item cap 扩展时（原创道具）：
./configure --enable-mechanics-hooks --with-item-id-cap=0xCE
```

- `FE8_EXPANSION_MECHANICS_HOOKS=0` 时整个注册表编译成空桩，**战斗数学与原版字节一致**。
- 容量上限 `EXPANSION_MECHANICS_MAX = 8`，别超。

**已可参考的官方范例**：`include/expansion_starter_content.h` 是官方给的"**config + 数据管线 + 运行时钩子**三者如何组合、且都不被特殊照顾"的完整示范——新增一个道具（`ITEM_EXPANSION_CE`）、一条作者态显示名、一个通过公开 API 注册的机制，**不碰 `src/bmbattle.c`、不为任何 stat 开后门**。你自己加系统时照这个结构抄。

### 12.4 贯穿三层的约束：ID 空间

`scripts/generated_data/idspace.py` 是**所有可扩展 ID 域（角色/职业/道具/章节/单位/事件）的单一事实来源**。

**两套契约，别搞混**：

| | DEFAULT（已提交） | ACTIVE（构建本地） |
|---|---|---|
| 位置 | `include/id_space.h`、`reports/id_space_audit.*` | `build/generated/data/id_space_active.h` |
| 道具上限 | 恒为 `0xCD` / 206 条 | 由本次构建决定（`FE8_ITEM_ID_CAP=0xCE` → 207 条） |
| 随 cap 变化？ | **永不** | 是，这就是它的职责 |
| 入库？ | 是 | 否（临时产物） |

**关键纪律**：**永远不要引用已提交的报告当作当前值**。要看当前构建的真实上限：

```bash
FE8_ITEM_ID_CAP=0xCE make generated-data-check
grep ITEM_ID build/generated/data/id_space_active.h
```

框架会在编译期静态断言 cap 与生成表长度一致（`ITEM_ID_CONFIGURED_CAP == ITEM_ID_ACTIVE_CONFIGURED_CAP`），**错配即编译失败**而非静默截断——这是保护你的机制，别想着绕过。

**对本项目的含义**：加原创道具/角色 = **扩 cap**，不是复用原版槽位。原版槽位留给原版内容，你的内容从 `*_EXPANSION_FIRST` 之后开始编号。

### 12.6 版本管理策略（重要待决）

框架**上游是活跃开发中的**（本机克隆在 `ec1dc855`）。你的改动如何与上游共存，需要尽早拍板：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A · 框架内分支**（当前状态） | 直接在 `fireemblem8-expansion` 里改，自己开分支推到自己的远端 | 最省事，马上能干活 | 与上游分叉，将来合并上游更新困难；框架仓库 2.5 GB |
| **B · 内容外置 + 构建脚本** | 框架当只读依赖（固定 commit），你的 `src/data/`、新 `.c`、`texts/` 单独放本仓库，构建前用脚本铺进去 | 与上游解耦，更新上游只需改一个 commit 号；本仓库变完整 | 需要一个 `sync` 脚本，多一层心智负担 |
| **C · fork + rebase** | fork 框架到自己账号，定期 rebase 上游 | GitHub 生态友好 | 冲突要手工解，框架改动频繁时很痛 |

**倾向方案 B**：符合"上游活跃 + 我只需要内容与少量机制扩展"的实际情况，且能让本仓库真正自洽（解决 §9 那个"换电脑丢内容"的问题）。

> **待用户拍板**。在做完这个决定前，内容仍散落在框架仓库里，换机有丢失风险。
