## 1. 总纲：拥有缝（owning seam）

### 1.1 一条铁律

框架对**每一类资产**都定义了唯一一个「**拥有缝**」——即：

> **哪张表 / 哪个链接列表 / 哪个运行时函数负责登记并消费这个资产**

**你的原创资产必须挂到同一个缝上，不得新建平行体系。**

这不是建议，是框架官方文档 `docs/community_asset_coverage.md` 写死的硬规则：

> 适配器必须保留已列出的拥有缝……**不得新增手工维护的表、链接列表或 ID 命名空间**。

### 1.2 为什么这条规则对你有利

乍看"必须挂到已有缝上"像是限制，实际上是**巨大的保护**：

| 好处    | 说明                              |
| ----- | ------------------------------- |
| 存档兼容  | 挂在既有表上 → 存档格式不变 → 不会因为加内容破坏玩家存档 |
| 上游可同步 | 不与框架分叉 → 框架升级时你的内容能平滑跟进         |
| 自动校验  | 现有校验器（schema、容量、引用完整性）会顺带检查你的内容 |
| 少写代码  | 大多数情况改数据/资产文件即可，不用写 C           |

### 1.3 四要素原则（**最容易被误解**）

框架明文规定：**创作文件是编译期输入，绝不是运行时格式**。

一个资产要被算作"已集成"，必须**四者齐备**：

| # | 要素            | 说明                                     |
| - | ------------- | -------------------------------------- |
| ① | **项目自有源文件包**  | 提交进 git 的源文件（PNG/TMX/MIDI），不是某个编辑器的导出物 |
| ② | **确定性校验/转换**  | 框架能重复、可验证地把源文件转成 ROM 用的格式              |
| ③ | **完整登记/链接接线** | 挂到了正确的运行时表/链接列表上                       |
| ④ | **一个运行时消费案例** | 能在游戏里真的被看到/听到                          |

> **⚠️ 关键警告**：在 **FEBuilderGBA / Event Assembler / Tiled** 里成功**预览、导入、导出**，**不等于**"框架支持"。
>
> 很多人以为"FEBuilderGBA 能导入 PNG 就能用"，实际上还需要 ②③④。**缺任何一环，资产就是"躺在磁盘上没进游戏"——而且往往不报错。**

### 1.4 五级成熟度

框架给每类资产标注了状态，**这直接决定你的工作量**：

| 状态                             | 含义                         | 你要做什么               |
| ------------------------------ | -------------------------- | ------------------- |
| **Supported**                  | 有完整"源文件 → 转换 → 运行时消费者"链路   | 照文档做，风险低            |
| **Partially supported**        | 底层能力齐备，但没有统一包格式/校验器管住登记与容量 | **能做，但参数要自己保证正确**   |
| **Manual-only**                | 运行时会消费，但创作必须直接改源码/表/链接脚本   | **工作量大，易错，须反复实机验证** |
| **Runtime capability missing** | 需要新的引擎能力，不只是格式转换           | **暂时别碰**            |
| **Out of scope**               | 外部工具格式，刻意不作为构建依赖           | 只能当参考               |

### 1.5 总对照表

| 原创资产       | 框架资产家族               | 成熟度      | 你的落点                        |
| ---------- | -------------------- | -------- | --------------------------- |
| 角色立绘 / 小头像 | Portraits & minimugs | 部分支持     | `content/assets/portraits/` |
| 战斗动画       | Battle animations    | **仅手工**  | `content/assets/banim/`     |

| 地图瓦片集      | Tilesets             | 部分支持     | `content/assets/tilesets/`  |
| 武器 / 道具图标  | Icons                | 部分支持     | `content/assets/icons/`     |
| 职业小图标      | Icons                | 部分支持     | `content/assets/unit_icon/` |

### 2.2 同步到框架的落点

| `content/assets/` | 同步到框架                   | 登记文件                                    |
| ----------------- | ----------------------- | --------------------------------------- |
| `portraits/<包>/`  | `assets/portraits/<包>/` | 合并 `assets/portrait_registry.json`      |
| `banim/<包>/`      | `assets/banim/<包>/`     | 合并 `assets/manifest.json`               |
| `tmx/*.tmx`       | `assets/tmx/`           | 合并 `assets/manifest.json`               |
| `spells/<包>/`     | `assets/manifests/`     | 合并 `assets/manifest.json`               |
| `tilesets/`       | `graphics/` 对应子目录       | `graphics_file_rules.mk` 规则             |
| `icons/`          | `graphics/item_icon/`   | 各消费者图标表                                 |
| `unit_icon/`      | `graphics/unit_icon/`   | 单位图标表                                   |
| `music/*.mid`     | `sound/songs/midi/`     | 追加 `sound/song_table.s` + 配置 `songs.mk` |
| `cg/`             | `graphics/cg/`          | 各屏数据                                    |

### 2.3 三个核心登记文件

框架的资产登记有**三个入口**，理解它们就理解了一切：

| 登记文件                                | 管什么                            | 你的合并方式           |
| ----------------------------------- | ------------------------------ | ---------------- |
| **`assets/manifest.json`**          | 版本化的**资产清单**（地图/动画/法术）         | 追加记录（每项有唯一 `id`） |
| **`assets/portrait_registry.json`** | 立绘的**类型化 FaceData 注册表**（172 条） | 按键合并（`id` 为键）    |
| **`sound/song_table.s`**            | 歌曲表 `gSongTable`               | 追加 `song` 行      |

> **★ 框架警告**：`assets/manifest.json` 是**唯一**的资产登记面。**不要额外新建表、链接列表或手工维护的生成文件。** 一切通过 manifest 的记录来表达。

### 2.4 通用转换能力（所有资产共享）

框架已有低层转换原语，你的原创资产**复用它们**：

| 关注点       | 契约                                                                | 证据                             |
| --------- | ----------------------------------------------------------------- | ------------------------------ |
| 索引图       | 提交的索引 PNG → 构建期 `.4bpp`                                           | `graphics_file_rules.mk`       |
| 调色板       | `.pal` → 构建期 `.gbapal`                                            | `graphics_file_rules.mk`       |
| 瓦片图 / TSA | 无头 `.map.bin`（运行时）vs 有头 `.tsa.bin`（运行时）——**由扩展名和消费者决定用哪个，不是字节形状** | `docs/tsa_audit.md`            |
| 图+TSA 成对  | FETSA 规则从 PNG 派生 `.feimgN.bin` + `.fetsaN.bin`                    | `graphics_file_rules.mk`       |
| LZ 压缩     | 提交资产是**规范/解压态**，`.lz` 是构建本地产物                                     | `docs/lz_suffix_diagnostic.md` |

## 3. 人物：立绘体系（最复杂的一类）

### 3.1 拥有缝

```
assets/portrait_registry.json  →  portrait_data[]  →  src/face.c 的 GetPortraitData()
                                          ↑
                            src/portrait_data.c（只 include 生成表，无手工初始化）
```

**另有一条独立的规则层**（重要）：

```
src/expansion_portraits.c  →  ExpansionPortrait_ResolveUnit() 等 API
```

`src/expansion_portraits.c` 是一个**项目可编辑的静态规则注册表**（190 行），用**声明顺序**求值，第一个命中的非零 ID 获胜。可用 `EXPANSION_PORTRAIT_MATCH_ANY` / `EXPANSION_PORTRAIT_CHAPTER_ANY` 做通配，也可用 flag 掩码做确定性规则。

**这对《山河烬》是重大便利**：如果想让"同一角色在不同章节穿不同衣服"，**不需要新增立绘 ID**，只需在规则表里加一条（章节选择器 + 不同 ID）。

### 3.2 硬上限（**最关键的数字**）

```
完整立绘 ID：  1 .. 0xAC          共 172 个槽位
通用小头像 ID：0x7F00 .. 0x7F07   共 8 个槽位（杂兵用）
```

**实测**：`assets/portrait_registry.json` 已有 **172 条记录**、`graphics/portrait/` 有 **1,038 个 PNG 切片**。

**结论：《山河烬》的 22 名原创角色必须「替换」原版角色的槽位，不能新增。**

→ **需要拍板的决策**：哪 22 个原版角色（艾莉卡、塞思……）被你的角色顶替。好消息是 172 槽只用 22 个，选择余地很大。

### 3.3 一张立绘包 = 一个目录 + 三个文件

**实测样例**（框架自带的艾莉卡包，`assets/portraits/eirika/`）：

```
eirika/
├── eirika.png       # 128×112 索引 PNG
├── eirika.pal       # JASC-PAL（可选）
└── metadata.json    # 必需
```

`metadata.json` 实测内容：

```json
{
  "schemaVersion": 1,
  "portraitId": 2,
  "symbol": "Eirika",
  "blinkKind": "FACE_BLINK_NORMAL",
  "anchors": { "mouth": [2, 6], "eyes": [3, 4] },
  "frames": {
    "main":         [0,  0, 80, 72],

    }
  }
```

### 3.4 ★ 六帧合一的固定网格（**核心知识**）

**一张 128×112 PNG 装 6 个部件**，位置是**固定契约，不可推断**：

```
┌──────────────────────────┬──────────────┐
│                          │              │
│      主脸 (80×72)        │  小头像      │
│      (0,0,80,72)         │  (80,0,32,32)│
│                          │              │
├────────┬────────┬────────┴──────┬───────┤
│ 眼开   │ 眼闭   │  嘴闭         │ 嘴开  │
│(0,72)  │(32,72) │  (64,72)      │(96,72)│
│ 32×16  │ 32×16  │   32×16       │ 32×16 │
└────────┴────────┴───────────────┴───────┘
总尺寸：128 × 112
```

**硬性要求**：

| 项      | 要求                                                                       |
| ------ | ------------------------------------------------------------------------ |
| PNG 格式 | **索引色**（indexed）、**非隔行**、恰好 **16 个调色板条目**                                |
| 透明     | **索引 0 必须透明**，且**不允许半透明**                                                |
| 尺寸     | 恰好 **128×112** 像素                                                        |
| 对齐     | 每个部件矩形在两个轴上**都必须是 8 的倍数**                                                |
| 调色板副档  | 可选同名 `JASC-PAL`（内容为 `JASC-PAL` / `0100` / 16 行 RGB），颜色须与 PNG 调色板**完全一致** |
| 路径     | 只允许 `assets/portraits/<包名>/<包名>.png` 及同名 `.pal`                          |

**`alias` 的两种模式**：

- `generated`：生成 4bpp 部件 + 确定性 GBA LZ77 流（**新资产用这个**）
- `existing-components`：只做迁移，精确命名已有部件符号（框架自带示例用的这个）

**生成细节**：4bpp 数据按 **GBA 8×8 瓦片顺序**输出，每字节**低半字节是左像素**——不是图像扫描线顺序。

### 3.5 美术减负方案

| 做法                     | 成本 | 效果                  | 推荐度   |
| ---------------------- | -- | ------------------- | ----- |
| 完全手绘 22 张原创立绘          | 极高 | 最好                  | 除非有画师 |
| **调色板派生 + 特征微调原版立绘**   | 低  | 与 §8 整体策略一致         | ★★★★★ |
| 复用原版改色 + 换发型/服饰局部      | 中  | 可接受                 | ★★★★☆ |
| AI 生成后手工修成 128×112 索引图 | 中高 | 需大量后期（索引色 + 16 色限制） | ★★☆☆☆ |

**框架明确不支持的**（manual-only）：**卡片图**（卡牌界面用）、**通用杂兵立绘**、**半身像格式**。

## 4. 地图：三套体系要分清

框架里"地图"是**三种完全不同的东西**：

| 名称         | 是什么                  | 位置                    | 成熟度     |
| ---------- | -------------------- | --------------------- | ------- |
| **章节地图布局** | 战斗地图瓦片排布（哪格是平原/森林/墙） | `assets/tmx/*.tmx`    | **已支持** |
| **地图变更**   | 事件导致的地形变化（如开闸门后变平地）  | 手写章节事件数据              | **仅手工** |
| **大地图**    | 世界地图（章节选择界面）         | `graphics/world_map/` | 独立体系    |

### 4.1 章节地图：完整的工具链（好消息）

**这是《山河烬》最省力的一类资产**——20 章地图可以用免费的 **Tiled 1.10.x** 绘制，走确定性管线：

```
content/assets/tmx/Ch0.tmx
        │
   [manifest 记录 + 校验]
        │
   [scripts/mar_to_map.py]  →  .mar / JSON
        │
   [常规规则]               →  .bin  →  LZ77  →  ROM
```

**构建命令**：

```bash
make assets-validate assets-generate assets-check assets-test
```

**生成物只落在** `build/generated/assets/tmx/`（不污染源码树）。

### 4.2 ★ `tmx-safe-v1` 的精确约束（**画地图必须遵守**）

| 区域         | 允许形式                                                                                                                 |
| ---------- | -------------------------------------------------------------------------------------------------------------------- |
| **XML**    | 必须以 `<?xml version="1.0" encoding="UTF-8"?>` 开头；仅 UTF-8 XML 1.0；≤512 KiB；≤16 个标记构造。**DTD、实体语法、注释、`&` 在 XML 展开前就被拒绝** |
| **TMX 版本** | `version="1.10"`、`tiledversion="1.10.x"`                                                                             |
| **地图**     | 恰好一个**有限** `orientation="orthogonal"` + `renderorder="right-down"` + `infinite="0"`；宽高 1..255；**16×16 元瓦片**          |
| **子元素**    | 恰好一个**内联**瓦片集 + 恰好一个图层。**分组、对象层、图像层、额外图层、属性、模板、未知 XML 全部拒绝**                                                         |
| **瓦片集**    | `firstgid="1"`、`name="fe8-metatiles-16px-4096"`、`tilecount="4096"`、`columns="64"`；**无子元素**（外部 TSX、图像、瓦片、变换、属性都不支持）   |
| **图层**     | 恰好 `id="1" name="Main"`，尺寸与地图一致；一个 `<data encoding="csv">` 子元素，**无压缩、无 chunk、无属性**                                   |
| **单元格**    | 恰好 `宽×高` 个 ASCII 十进制 CSV GID；GID 范围 **1..4096**；`gid - 1` 即 FE8 13 位元瓦片 ID。**零、负数、溢出、越界、Tiled 翻转/旋转标志位全部失败**         |

**GID 映射契约**：GID 1 ↔ FE8 元瓦片 0；GID 4096 ↔ 4095。这是**显式映射**，不是图形导入——**瓦片集本身的图形/调色板/配置是另一项独立能力**，需要单独准备。

### 4.3 地图变更（地形事件）—— 需要额外预算

如果你的章节设计里有"**打开闸门后这里变成平地**""**烧毁桥梁后不可通行**"这类地形变化：

- 运行时支持：有（`struct ROMChapterData.map.changeLayerId`）
- 创作支持：**无**（Manual-only，需直接改章节事件数据）
- 校验器：**无**（矩形、瓦片数、事件顺序、地图边界都没有统一校验）

→ **设计章节时要把这类需求单独列出来，预留工时。**

## 5. 音乐：最大的一块现成资产

### 5.1 拥有缝

```
sound/songs/midi/*.mid  →  mid2agb  →  sound/song_table.s 的 gSongTable  →  M4A 播放器
                                             ↑
                                    songs.mk（逐歌参数）
```

**另有一条 BGM 路由层**（`include/expansion_bgm.h`）：

- `ExpansionBgm_Start` / `ExpansionBgm_Change`：常规上下文
- `ExpansionBgm_StartExplicit` / `ExpansionBgm_ChangeExplicit` / `ExpansionBgm_Override`：事件/战斗动画显式覆盖
- **`src/data/bgm_registry.json`**：窄而类型化的创作面，接受**章节/上下文/flag 变体**和**舞者/杖选择器**
- 当前注册表是**空的**（默认行为惰性，保留原版全部曲目）


**这对《山河烬》很有用**：想让"某章的战斗曲不同""某个 flag 触发后换曲"，用 `bgm_registry.json` 配置即可，**不用写代码**。

**flag 约束**：章节 flag `1..40`、永久 flag `101..300`；`0` 和 `100` 是非存储哨兵值，会被拒绝。

### 5.2 实测规模

| 项        | 数字        |
| -------- | --------- |
| MIDI 源文件 | **589 个** |
| 歌曲表      | 约 1,000 行 |

**命名规律清晰**（可直接检索复用）：

```
song001_agbfe3_bgm_opening     片头
song002_agbfe3_bgm_op_theme_i  开场主题
song003_agbfe3_bgm_pro_first   序章
song004-008_..._wmap_01..05    世界地图
song009-015_..._map_pl2..pl12  玩家回合战斗曲
```

歌曲表条目格式：

```asm
song song001_agbfe3_bgm_opening, 0, 0     @ 符号, 优先级, 混响组
song song004_agbfe3_bgm_wmap_01, 1, 1
```

### 5.3 你该怎么用

| 做法            | 工作量 | 建议阶段                                     |
| ------------- | --- | ---------------------------------------- |
| **复用原版 BGM**  | 零   | **Demo 五章全部用这个**                         |
| **改编原版 MIDI** | 低   | 想做"中国风"就改配器/调式                           |
| **原创 MIDI**   | 中   | 用任意 DAW 导出 `.mid` 放进 `sound/songs/midi/` |

**注册一首歌要做三件事**（缺一不可）：

1. 放 `.mid` 到 `sound/songs/midi/`
2. 在 `songs.mk` 配 **voicegroup（音色组）/ reverb（混响）/ priority（优先级）/ volume（音量）**
3. 在 `sound/song_table.s` 加一行 `song <符号>, <优先级>, <混响>`

> **⚠️ 框架提醒**：**一个 MIDI 转换成功 ≠ 已注册。** 必须完成歌曲表与路由的登记才算。

### 5.4 资源约束（无统一校验器）

以下全部**没有**统一的包校验器，属于 partially supported：

- voicegroup 分配
- 序列 / 播放器分配
- 优先级、混响
- **采样内存**
- **同时发声声道预算**

→ **实践建议**：新 BGM **一次加 1~2 首**，实机确认后再加。加太多可能挤爆采样内存。

## 8. ★ 美术减负总原则

**框架自带资产是"白送的画风还原"，你的原创应该尽量"派生"而非"新建"。**

| 手段                  | 成本 | 适用                |
| ------------------- | -- | ----------------- |
| **复用**（直接用原版）       | 零  | 战斗动画、UI、瓦片、音效、BGM |
| **调色板派生**（换配色）      | 极低 | 势力配色、装备品阶、神器发光    |
| **数值重排**（不碰美术）      | 零  | 武器档位、职业基值、成长率     |
| **局部改绘**（换发型/服饰/旗帜） | 低  | 立绘、单位图标           |
| **全新绘制**            | 高  | 只留给主角与关键反派        |

**这条原则直接来自技术选型的初衷**：选 FE8 反汇编框架的全部理由就是"**100% 还原原版画风**"。如果大量新建美术，这个优势就浪费了。

## 11. 验证方法：怎么确认资产真的进游戏了

**这是最容易出问题的地方**——资产缺"登记"或"接线"时**往往不报错**。

### 11.1 四层验证

| 层         | 命令 / 手段                                 | 能发现什么                              |
| --------- | --------------------------------------- | ---------------------------------- |
| **清单校验**  | `make assets-validate`                  | manifest 记录格式、源文件路径、依赖、所有权冲突、容量、溯源 |
| **生成**    | `make assets-generate`                  | 转换是否成功                             |
| **反查**    | `make assets-check`                     | 生成物与源是否一致（漂移检测）                    |
| **构建后反查** | 在 `build/.../fireemblem8.map` 里 grep 符号 | **资产是否真的被 LOAD 进 ROM**             |

### 11.2 完整验证流程

```bash
# 1. 资产管线四动词
make assets-validate assets-generate assets-check assets-test

# 2. 全量构建（含 boot-check）
make

# 3. 反查（关键！）
grep -n "<你的资产符号>" build/expansion-modern/release/aapcs/fireemblem8.map

# 4. 实机确认
mGBA 打开 ROM 目视/耳听
```

**第 3 步是"四要素"里第 ③ 项的验证**——如果符号没出现在 map 里，说明接线没做成功。

### 11.3 反例（必须警惕）

| 症状                                | 真实原因                                |
| --------------------------------- | ----------------------------------- |
| PNG 放进目录、构建成功、游戏里看不到              | manifest 没加记录（缺要素 ③）                |
| manifest 加了记录、但还是看不到              | 没 `touch Makefile` 强制重解析（新增文件的通病）   |
| `make assets-validate` 过了、游戏里是旧素材 | 生成物是旧的；跑 `assets-check` 看漂移         |
| MIDI 转换成功、游戏里没声音                  | `song_table.s` 没加行（框架明文：转换成功 ≠ 已注册） |
