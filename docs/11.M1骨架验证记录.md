### ⚠️ `probe_file` 的一个实测教训

初版我按记忆写成 `mgfembp/mgfembp.lds.s`，DRY_RUN 时**误报「子模块未就绪」**。
查真实目录可见文件名是 **`mgfembp.lds`**（无 `.s`）。

**教训**：探针路径必须来自 `ls` 实测，不能抄报错。

## 5. ★ 合并逻辑的正/负向测试（R-17 防护）

### 5.1 正向：槽位替换成功

测试补丁 `content/data/characters.json` 含 1 条原创角色（`characterId: 3`，对应 D-1 定案的「裴松年↔吉利亚姆」）：

```
━━━━━━ 第 3 步 / 铺设 ━━━━━━
  ✓ [merge] characters.json 应用 1 条
        · CHARACTER_GILLIAM → CHARACTER_PEI_SONGNIAN
```

### 5.2 负向 1：越界 characterId → 拦截

注入 `characterId: 9999`：

```
  ✗ [characters.json] 补丁 characterId=9999 越界（合法 1..256）
  ✗ 合并 characters.json 失败
```

✅ **在写入前中止，未污染框架**。

### 5.3 负向 2：缺 characterId → 拒绝猜测

移除条目的 `characterId` 键（只剩 `character` 符号名）：

```
  ✗ [characters.json] 补丁条目缺 characterId（无法定位槽位）：CHARACTER_PEI_SONGNIAN
  ✗ 合并 characters.json 失败
```

✅ **不猜符号名对应哪个槽位** —— 这正是 R-17 要求的「不许猜」。

### 5.4 为什么必须这样防（R-17 的本质）

框架 `characters.json` 的 256 条分两套互斥键方案：

| 形态 | 条数 | 定位键 | 实测 |
|---|---|---|---|
| 具名角色 | 94 | `character`（符号名） | 下标 0 = `CHARACTER_EIRIKA` |
| 无名杂兵 | 162 | `characterId`（**1-based**） | 下标 26 → `characterId` 27 |

两个致命点：
1. 用 `c["character"]` 取键 → 那 162 条**没有这个键** → `KeyError`
2. `characterId == 下标 + 1` → **按下标定位整体偏移一格**（把角色数值写到隔壁槽位）

**脚本的处理**：合并前先遍历全表，断言每条 `characterId == idx + 1`（不符即中止），
再按 `characterId` 定位替换。**这是 R-17 的完整落地。**

## 7. ⚠️ 为什么禁用上游 `expansion-modern-boot-check`

**实测证据**：

| 位置 | 内容 |
|---|---|
| `modern.mk:2814` | `expansion-modern-boot-check: …` → 调 `gba_playtest.py verify --policy behavior` |
| `gba_playtest.py:2917-2932` | `behavior` 策略**只排除顶层 `rom` 键**，其余全部严格比对 |
| `tools/gba-playtest/fingerprints/boot.json` | 含 `framebuffer_hash: "fnv1a64-rgb24:…"`（frame 0/60/120 **逐帧像素哈希**） |

**推论**：一旦启用中文（字库扩容 + 菜单/title 文字中文化），title 画面像素必然改变
→ `framebuffer_hash` 不匹配 → **该目标必然失败**。这不是 bug，而是它本就不为改版项目设计。

**本项目改用自建五项校验**（`tools/shanhe-build.sh` 第 5 步）：

| # | 检查项 | 方法 |
|---|---|---|
| ① | ROM 存在 | `test -f` |
| ② | 尺寸正确 | `33554432` 字节 |
| ③ | header 正确 | `0xA0` 起 12 字节 == `FIREEMBLEM2E`；`0xAC` 起 4 字节 == `BE8E` |
| ④ | 可引导 | mGBA 无头跑 60 帧不崩溃 |
| ⑤ | 中文可见 | ROM ≥ 32M（含 locale bank）+ 人工目视 |

## 10. M2 前置调研：原创角色入表通道（✅ 已完成）

> 2026-09-25 完成。四条出路全部实测，结论已写回 `6.方案B内容外置规划.md` §3.4b。

**关键事实**：`src/data_characters.c` 不只是 round-trip 参考，被 **3 条管线**同时使用——① `characters/parser.py`（round-trip）② `fixed_width_labels.py:30`（角色名固定宽度标签）③ `crosswalk.py:306`（原版对照）；`modern.mk:2399` 依赖 ②③。**它必须存在且与 JSON 一致。**

**实测结论表**：

| 出路 | 做法 | 实测 |
|---|---|---|
| A. items 式豁免 | `characters_expansion.json` + 豁免 | ❌ 框架无此机制（仅 items 有），改框架违反铁律① |
| B. 双写（手写维护） | JSON + 手写 patch `src/data_characters.c` | ✅ 完整 make 通过（ROM `b64d264a`）|
| **B'. 生成产物回填** ★ | JSON → `generate --no-roundtrip` → 覆盖 `src/data_characters.c` | ✅ **完整 make 通过，ROM 与 B 逐字节相同（`b64d264a`）** |
| C. 运行时 C 改写 | 原创 `shanhe_*.c` 改 `gCharacterData[]` | ⚠️ 未实测 |
| D. 移走手写 C | 删除 `src/data_characters.c` 让 round-trip 跳过 | ❌ **否决**——`modern.mk:2399` 报 `No such file`（本地化管线读它）|

**★ 定案：B'（生成产物回填）**。全自动、round-trip 自动通过、产物语义正确。唯一框架侧改动是 `src/data_characters.c`（脚本自动回填，可 `RESTORE=1` 还原，已写入 `docs/6` §1.3 铁律①例外）。

**副发现**：`expansion-modern-boot-check` 对"改角色数值"**不敏感**（改 `baseLevel` 后仍 passed），只对"改中文/字库"敏感。
