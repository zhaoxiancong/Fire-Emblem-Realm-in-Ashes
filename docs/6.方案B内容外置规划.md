#### ⚠️ 关于"覆盖会不会把能跑的版本弄丢"（重要）

**不会。** 三条独立保障，任一失效都不会丢数据：

| 保障 | 实测证据 | 恢复方式 |
|---|---|---|
| **① git 追踪** | `src/data/*.json` 共 19 个文件、`texts/` 共 91 个文件**全部被 git 追踪**；工作区 0 处改动 | `git checkout -- src/data/ texts/` |
| **② 上游远端在线** | `git ls-remote origin master` 返回 `ec1dc855...` | 删掉整个目录重新 `git clone` |
| **③ 本仓库持有内容** | 方案 B 的核心：你的内容全在 `content/`，另有 git 保护 | 重跑 `shanhe-build.sh` |

**实测验证**（2026-09-25）：故意把 `characters.json` 改成 `{"broken": true}`，SHA1 从 `6cbf4ee7` 变为 `e3522cc0`；执行 `git checkout -- src/data/characters.json` 后 SHA1 **恢复为 `6cbf4ee7`，与原文件逐字节一致**。

**因此，脚本的"写入"操作本质是"可逆的临时改动"**——就像你在编辑器里改了一行然后撤销。而 `shanhe-build.sh` 的**第 5 步反查**会随时告诉你"框架里有哪些被改动了"，第 6 步还能一键还原（见 §3.3）。

> **术语修正**：规划早期版本用过"被覆盖"这个说法，容易让人误以为原数据被销毁。准确表述是「**由脚本合并写入，且随时可 `git checkout` 还原**」。

### 1.3 三条铁律

1. **框架仓库里永远不出现手改。** 任何改动都先写进 `content/`，再由脚本铺过去。
2. **`framework.lock` 是唯一的上游依赖声明。** 升级框架 = 改这一行 + 重跑构建 + 跑回归。
3. **两边都要能自证。** 脚本跑完必须反查框架侧有无"未纳管的改动"（防止手滑直接改框架）。

### 1.4 安全操作纪律

为了把"可恢复"落实到日常习惯：

- **进框架仓库前先看一眼**：`git -C ~/projects/fireemblem8-expansion status --short`——干净才动手。
- **只在 `content/` 里编辑**。养成习惯后根本不会去碰框架。
- **`shanhe-build.sh` 已内建还原子命令**（见 §3.3），不确定时先 `RESTORE=1` 归零再重来。
- **不要 `git commit` 框架仓库**。它应该是永远"有未提交改动"的状态（那是脚本铺进去的内容），提交了反而会把上游历史搞乱。
- **`git clean` 要极其小心**：`git clean -fd` 会删掉未追踪文件。框架仓库里未追踪文件主要是构建产物，但若 `content/src/` 追加的新 `.c` 未被正确纳入，可能被误删。**别在框架仓库跑 `git clean`。**

## 2. 原创资产体系（美术 / 武器 / 地图 / 音乐 / 文本）

> 本节回应"原创美术和资产一般包括人物、武器、地图、音乐等，这部分和框架自带资产的对应关系是什么"。
>
> **核心方法**：框架对每一类资产都有一个**「拥有缝（owning seam）」**——即"哪张表、哪个链接列表、哪个运行时消费者负责登记这个资产"。**你的原创资产必须挂到同一个缝上**，而不是新建平行体系。框架官方文档 `docs/community_asset_coverage.md` 把这条写成了硬规则：
>
> > 适配器必须保留已列出的拥有缝……**不得新增手工维护的表、链接列表或 ID 命名空间**。

### 2.0 一句话对应关系表

| 你的原创资产 | 框架对应资产家族 | 你的文件放哪 | 挂到哪个缝 | 成熟度 |
|---|---|---|---|---|
| 角色立绘 / 小头像 | Portraits & minimugs | `content/assets/portraits/` | `assets/portrait_registry.json` → `portrait_data[]` | 部分支持 |
| 战斗动画 | Battle animations | `content/assets/banim/` | `banim_data[]` + `linker_script_banim.txt` | 仅手工 |
| 地图布局 | Chapter map layouts | `content/assets/tmx/` | `assets/manifest.json` → `gChapterDataAssetTable` | **已支持** |
| 地图图块集 | Tilesets | `content/assets/tilesets/` | `gChapterDataAssetTable` 的 `objNId`/`paletteId` | 部分支持 |
| 武器 / 道具图标 | Icons & map sprites | `content/assets/icons/` | 各消费者图标数组 | 部分支持 |
| 单位小图标（职业图标） | Icons | `content/assets/unit_icon/` | 单位图标表 | 部分支持 |
| 音乐 / BGM | Music & SFX | `content/assets/music/` | `sound/song_table.s` 的 `gSongTable` | 部分支持 |
| 音效 | Music & SFX | `content/assets/sfx/` | 直录音源工具链 | 部分支持 |
| 法术 / 魔法特效 | Spell animations | `content/assets/spells/` | `SpellAssoc` + `StartSpellAnimation` | **已支持（窄子集）** |
| 事件 CG / 背景 | Backgrounds & TSA | `content/assets/cg/` | 各屏数据 + 图形规则 | 部分支持 |
| **武器数据（数值）** | **不是资产，是数据** | `content/data/items*.json` | 生成数据平台 | **已支持** |
| **文本（剧情/UI）** | Localization | `content/texts/` | `ExpansionMsgId` 目录 | **已支持** |

**关键区分：武器不是"资产"，是"数据"。** 武器的**图标**是资产，武器的**数值/名称/耐久**是 `items.json` 里的数据。见 §2.3。

### 2.1 五级成熟度（决定你的工作量）

框架为每一类资产定义了状态。理解它，你就能预判"做这个东西要花多少力气"：

| 状态 | 含义 | 对《山河烬》意味着 |
|---|---|---|
| **Supported** | 有完整的"源文件 → 确定性转换 → 运行时消费者"链路；加一个新资产可能仍需手工登记 | 照文档做就行 |
| **Partially supported** | 底层能力都有，但没有一个统一的包格式/校验器管住登记与容量 | **能做，但你要自己保证参数正确** |
| **Manual-only** | 运行时会消费，但创作必须直接改源码/表/链接脚本，没有社区格式适配器 | **工作量大，容易错，需要反复实机验证** |
| **Runtime capability missing** | 需要新的引擎能力，不只是格式转换 | **暂时别碰**（如新的魔法动画类型） |
| **Out of scope** | 外部工具格式，刻意不作为正常构建依赖 | 只能当参考，不能进构建 |

**★ 重要纪律（框架明文规定）**：

> 创作文件是**编译期输入**，绝不是运行时格式。TMX 地图、格式化立绘、Event Assembler 事件文件、编辑器战斗动画包——**都不能在运行时喂给 ROM**。
>
> **在 FEBuilderGBA / Event Assembler / Tiled 里成功预览、导入、导出，不等于"已支持"。**

这条经常被误解。很多人以为"FEBuilderGBA 能导入 PNG 就能用"，实际上还需要：**项目自有的源文件包 + 确定性校验/转换 + 完整的登记/链接接线 + 一个运行时消费案例**。四者齐备才算。

### 2.2 通用转换能力（所有资产共享的底层）

框架已经有一套低层转换原语，你的原创资产**复用它们**，不需要自己写转换工具：

| 关注点 | 契约 | 证据文件 |
|---|---|---|
| 索引图（indexed PNG） | 提交的索引 PNG → 构建期 `.4bpp`；按家族规则限制图块数 | `graphics_file_rules.mk` |
| 调色板 | `.pal` → 构建期 `.gbapal`；`.agbpal` 仅在编码/数据形状需要时作为二进制规范源 | `graphics_file_rules.mk` |
| 瓦片图 / TSA | 无头 `.map.bin`（运行时）vs 有头自底向上 `.tsa.bin`（运行时）——**是扩展名和消费者决定用哪个，不是字节形状** | `docs/tsa_audit.md` |
| 图+TSA 成对生成 | FETSA 规则从 PNG 派生每屏 image/TSA，支持逐资产选项 | `graphics_file_rules.mk` |
| LZ 压缩 | 提交的资产是**规范/解压态**，`.lz` 是构建本地产物；需要精确复现旧流时用 `LZ_FLAGS := -mindist N` | `docs/lz_suffix_diagnostic.md` |
| 类型化游戏数据 | 生成数据平台有 validate/generate/check/test 四动词（**不是**资产包注册表，不要重复造） | `docs/generated_data.md` |

> ⚠️ **注意**：这些原语**都不会自动登记新资产**。你把 PNG 转成 `.4bpp` 只完成了一半，还必须把它接到对应的运行时表上。

### 2.3 武器：数据与资产要分开看

这是个常见混淆点，必须讲清：

| 部分 | 性质 | 位置 | 对应框架机制 |
|---|---|---|---|
| 武器数值（威力/命中/必杀/重量/耐久/价格/熟练度档位） | **数据** | `content/data/items.json` | 生成数据平台（三动词） |
| 武器名称 / 描述文本 | **文本** | `content/texts/expansion/catalog.zh-Hans.json` | `ExpansionMsgId` 目录 |
| 武器图标（背包/商店里的 16×16 小图） | **资产** | `content/assets/icons/` | 图标表（partially supported） |
| 武器特效（挥砍动画、法术特效） | **资产** | 战斗动画 / 法术包 | `banim_data[]` / `SpellAssoc` |
| 武器三角克制关系 | **数据** | `content/data/weapontriangle.json` | 生成数据平台（见 §5） |

**《山河烬》的武器五档 C/B/A/S/★** 全部落地在 `items.json` 的数值字段里 —— **零 C 代码**。只有神器特有的**图标**和**特效**才需要资产工作。

**武器的"档位"怎么表达？** 框架没有"档位"这个原生概念。三种做法，按推荐度：

1. **命名前缀 + 数值排序**（推荐，零侵入）：如 `铁枪` / `钢枪` / `银枪` / `玄铁孤枪` / `破军枪`，靠数值区分档位。原版就是这么做的。
2. **武器熟练度门槛**（框架原生）：`itype` + `wexp` 门槛已有，用 `WPN_EXP_C/B/A/S` 表达准入门槛。
3. **新增道具 ID 空间**：若需要框架没有的字段（如"黯淡耐久机制"），走 `--with-item-id-cap` 扩 ID 空间（见 §2.8）。

### 2.4 人物：立绘体系（最复杂的一类）

**对应关系**：`assets/portrait_registry.json` → `portrait_data[]` → `src/face.c` 的 `GetPortraitData()`

#### 2.4.1 框架现有规模

| 项目 | 实测数字 |
|---|---|
| 立绘注册表条目 | **172 条**（含眨眼变体） |
| 其中 `FACE_BLINK_NORMAL` | 160 条 |
| 其中 `FACE_BLINK_CLOSED` | 12 条 |
| 立绘 PNG 文件 | **1,038 个**（含切片） |
| CG 图 | **330 个** |

**★ 立绘 ID 的硬上限**（`docs/portrait_resolver.md`）：

```
完整立绘 ID：  1 .. 0xAC        （共 172 个槽位）
通用小头像 ID：0x7F00 .. 0x7F07 （8 个槽位，给杂兵用）
```

**这对《山河烬》是硬约束**：172 个立绘槽位，原版已用满。你的 22 名原创角色**必须复用或替换原版槽位**。（好消息：22 个远小于 172，只需选 22 个原版角色的立绘槽改掉。）

#### 2.4.2 一条立绘记录包含什么

`portrait_registry.json` 单条结构：

```json
{
  "id": 2,
  "img": "portrait_Eirika_tileset",       // 主图瓦片集
  "imgChibi": "portrait_Eirika_chibi",    // 小头像（地图/状态栏用）
  "pal": "portrait_Eirika_palette",       // 调色板
  "imgMouth": "portrait_Eirika_mouth",    // 嘴部差分
  "imgCard": null,                        // 卡片图（可选）
  "xMouth": 2, "yMouth": 6,               // 嘴部坐标
  "xEyes": 3, "yEyes": 4,                 // 眼部坐标
  "blinkKind": "FACE_BLINK_NORMAL"        // 眨眼类型
}
```

**这意味着做一套原创立绘要准备 4~5 张图**：主图瓦片集、小头像、调色板、嘴部差分、可选卡片。

#### 2.4.3 美术减负方案（重要）

框架文档提到支持的格式是 **"严格的 FE7/FE8 128×112 格式化全身立绘包"**（`formatted-portrait-package`）。

**对《山河烬》的现实建议**：

| 做法 | 成本 | 效果 |
|---|---|---|
| 完全手绘 22 张原创立绘 | 极高 | 最好但不可能（除非有画师） |
| **调色板派生 + 特征微调原版立绘** | 低 | **推荐**——与 §2.10 的整体减负策略一致 |
| 复用原版立绘改色 + 换发型/服饰局部 | 中 | 可接受 |
| 用 AI 生成后手工修成 128×112 索引图 | 中高 | 需大量后期处理才能符合 GBA 索引色 |

**框架明确不支持的**：卡片图（`imgCard`）、通用杂兵立绘、半身像格式 —— 这些是 **manual-only**，需要直接改 `portrait_data.c` 和符号接线。

### 2.5 地图：两套体系要分清

**这是最容易搞混的一块**，因为框架里"地图"有三种完全不同的东西：

| 名称 | 是什么 | 对应文件 | 成熟度 |
|---|---|---|---|
| **章节地图布局** | 战斗地图的瓦片排布（哪些格子是平原/森林/墙） | `assets/tmx/*.tmx` → `.bin` | **Supported** |
| **地图变更** | 事件导致的地形变化（如"打开闸门后这里变成平地"） | 手写章节事件数据 | **Manual-only** |
| **大地图** | 世界地图（章节选择界面） | `graphics/world_map/` | 独立体系 |

#### 2.5.1 章节地图（有完整工具链）

框架提供了 **TMX 安全子集**（`tmx-safe-v1`）—— 可以用 **Tiled 1.10.x** 这个免费开源工具绘制地图，然后走管线生成：

```
assets/tmx/Ch2Map.tmx   ──[manifest 校验]──→ .mar/JSON
                              │
                        [scripts/mar_to_map.py]
                              ↓
                        .bin 负载 ──[LZ77]──→ ROM
```

**★ 硬约束（`txm-save-v1` 校验的）**：

| 约束 | 值 |
|---|---|
| 地图尺寸 | 1..255（`u8`） |
| GID 映射范围 | 4096 |
| 地图缓冲区容量 | **2048 字节** |
| 图层 | **仅正交、单图层** |
| 压缩 | LZ77 |

**明确不支持的**：多图层、变换、外部瓦片集、其他编辑器导出格式、地图变更。

**对《山河烬》的意义**：**20 章的战斗地图可以用 Tiled 画**，这是好消息。但注意单图层 + 2048 字节缓冲的约束，以及瓦片集本身要另行准备。

#### 2.5.2 验证方式

`docs/tmx_map_layouts.md` 是权威格式说明；校验是**确定性的**（语法、所有权、源安全、漂移、对抗性 TMX 都测）。

### 2.6 音乐：最大的一块现成资产

**对应关系**：`sound/songs/midi/*.mid` → `mid2agb` 转换 → `sound/song_table.s` 的 `gSongTable` → M4A 播放器

#### 2.6.1 框架现有规模

| 项目 | 实测数字 |
|---|---|
| MIDI 源文件 | **589 个** |
| 歌曲表长度 | 约 1,000 行（含注释） |

歌曲表条目格式：

```asm
song song001_agbfe3_bgm_opening, 0, 0     @ 歌曲符号, 优先级, 混响组
song song004_agbfe3_bgm_wmap_01, 1, 1
```

**命名规律清晰**：`songNNN_agbfe3_bgm_<用途>.mid` —— `opening`（片头）、`op_theme`（开场主题）、`pro_first`（序章）、`wmap_01..05`（世界地图）、`map_pl2..pl12`（玩家回合战斗曲）。**原版的全部音乐都是可读的 MIDI**。

#### 2.6.2 你能做什么

| 做法 | 说明 |
|---|---|
| **复用原版 BGM** | 直接引用 `gSongTable` 里已有条目，零工作量。**Demo 五章先用这个。** |
| **自己写 MIDI** | 用任意 DAW 导出 `.mid`，放进 `sound/songs/midi/`，在 `songs.mk` 注册（voicegroup/混响/优先级/音量），在 `song_table.s` 加一行 |
| **改编原版** | MIDI 可编辑，改调式/乐器即可做出"中国风改编版" |

**★ `songs.mk` 每首歌要配的参数**：voicegroup（音色组）、reverb（混响）、priority（优先级）、volume（音量）。这是**逐歌配置**，不是自动的。

**M4A 引擎的资源约束**：voicegroup 分配、序列/播放器分配、优先级、混响、采样内存、同时发声声道预算 —— 这些**没有一个统一的包校验器**，属于 partially supported。加太多 BGM 可能挤爆采样内存，需要逐首试。

#### 2.6.3 《山河烬》的音频规划

原设计文档提到 **Demo 8 首 BGM**。建议：

- **Demo 阶段**：优先复用原版 BGM（589 个库里挑），零风险
- **正式阶段**：新增原创曲走 `song_table.s` 注册，一次加 1~2 首验证采样内存
- 注意"中国风"需求：原版是西方奇幻风，改编成本主要在**配器与调式**，不在技术

### 2.7 战斗动画：工作量大，能砍就砍

**对应关系**：`banim_data[]`（`src/banim_data.c`）→ 职业/单位动画定义 → `linker_script_banim.txt` 决定压缩与链接顺序

#### 2.7.1 框架现有规模

| 项目 | 实测数字 |
|---|---|
| `banim_data[]` 条目 | **208** |
| 战斗动画 PNG | **470 个** |

**★ 硬约束**：`struct BattleAnim.abbr` **只有 12 字节**（动画缩写名）。且一个完整动画的资源契约包括：表索引、职业引用、脚本/OAM 形状、调色板槽位、VRAM/OAM 占用、链接顺序 —— **没有任何一个校验器同时检查这些**。

**成熟度 = Manual-only**：没有社区格式适配器，必须直接改源码/表/链接脚本。

#### 2.7.2 框架提供的包格式（但不覆盖完整注册）

框架有一个 `battle-animation-package` v1 示例（`assets/banim/lorm_sp1/`）：

```json
{
  "schemaVersion": "fe8.community-banim.v1",
  "id": "LORM_SP1_PROOF",
  "abbreviation": "lorm_sp1",
  "animConf": "AnimConf_90",
  "class": "CLASS_MOGALL",
  "weaponType": "ITYPE_DARK",
  "frames": [{ "id": "idle", "path": "..." }],
  "resources": {
    "maxFrames": 1, "maxSheetTiles": 256,
    "maxOamPerFrame": 32, "maxPaletteColors": 16
  }
}
```

**注意**：这只是**一个证明案例**（"proof"），不是通用适配器。框架明文说 #62 issue 才拥有"完整包转换、表/职业/链接生成、容量检查"。

#### 2.7.3 《山河烬》的减负策略（重要）

**战斗动画是整个项目里单位成本最高的美术工作**（每个职业每类武器一套，含待机/攻击/被击/必杀多套）。

推荐策略：

| 优先级 | 做法 |
|---|---|
| **最高** | **复用原版动画**。你的职业若与原版职业形态相近（剑士/骑兵/弓手/法师），直接复用原版动画，只改配色 |
| 高 | **调色板派生**。同一套动画换个调色板就是"新势力配色"，零骨架成本 |
| 中 | 只给**主角和关键角色**做原创动画 |
| 低 | 杂兵/敌将全部复用 |

这与 §2.10 的整体减负原则一致：**框架原版资产是"白送的画风还原"，不要重复造**。

### 2.8 神器与原创机制：走 ID 空间扩展

《山河烬》的**神器（9 件）**、**凶相双血条**、**三才法环**这类原创机制，涉及框架没有的能力。

#### 2.8.1 道具 ID 空间扩展（神器用）

框架的 ID 空间是**双契约**设计：

| 契约 | 位置 | 道具上限 |
|---|---|---|
| **DEFAULT**（已提交） | `include/id_space.h` | 恒为 `0xCD`（206 条） |
| **ACTIVE**（构建本地） | `build/generated/data/id_space_active.h` | 随 `FE8_ITEM_ID_CAP` 变 |

**加原创道具的正确做法 = 扩 cap，不复用原版槽位**：

```bash
./configure --with-item-id-cap=0xCE    # 206 → 207
```

框架在编译期做静态断言（`ITEM_ID_CONFIGURED_CAP == ITEM_ID_ACTIVE_CONFIGURED_CAP`），错配即失败 —— **别想绕过**。

> **纪律**：永不引用已提交的 `reports/id_space_audit.*` 当作当前值 —— 那是 DEFAULT 契约的快照，不是构建配置。

#### 2.8.2 法术特效（有窄支持）

框架支持一个**严格子集** `custom-spell-effect`（`feditor-magic-v1`）：

- 接受：`spell.json` + 文本 + 索引 PNG 包
- **拒绝**：CSA、任意命令/C、补丁二进制、ROM 篡改、外部 TSA/OAM
- 容量上限（fail-closed）：1..64 帧、255 ticks、OBJ `0x1000`、BG `0x2000`、1200 字节 TSA、16 OAM、8 SFX、总量 `0x40000`
- ID：`CUSTOM_SPELL_*` → 私有密集索引 `0x80..0x8F`（**只有 16 个**）

**对《山河烬》**：神器的特殊特效若走这条路，注意 **16 个 ID 上限**。

#### 2.8.3 机制代码（凶相/三才法环用）

走 `content/src/shanhe_*.c` + `ExpansionMechanicsRegister()`。**关键限制见 `7.框架架构与机制详解.md` §6.3**：

> **apply 顺序陷阱**：apply #1 时 `context->opponent` 的战斗数值**尚未计算**。读 `opponent->battleAttack/battleDefense/battleHitRate` 是真 bug。
>
> 安全输入 = subject 自身战斗数值 + opponent 的**底层 unit 数据**（职业/等级/状态/位置/HP）。

**推论**：需要**双方最终数值**的机制（如克制关系判定）**不能挂这个 seam**。兵刃三环/三才法环走 JSON（§5）而非 C 钩子，正是因为这个。

### 2.10 ★ 美术减负总原则

**框架自带资产是"白送的画风还原"，你的原创应该尽量"派生"而非"新建"。**

按成本从低到高：

| 手段 | 成本 | 适用 |
|---|---|---|
| **复用**（直接用原版资产） | 零 | 战斗动画、UI、地图瓦片、音效 |
| **调色板派生**（换配色） | 极低 | 势力配色、装备品阶色、神器发光色 |

| **数值重排**（不碰美术，只改数据） | 零 | 武器档位、职业基值、成长率 |
| **全新绘制** | 高 | 只留给主角与关键反派 |

**这条原则直接来自技术选型的初衷**：选 FE8 反汇编框架的全部理由就是"100% 还原原版画风"。如果大量新建美术，这个优势就浪费了。

## 3. 同步机制设计（`tools/shanhe-build.sh`）

### 3.1 六个步骤

| 步 | 动作 | 失败处理 |
|---|---|---|
| **0** | **安全预检**：框架仓库工作区是否干净 | 不干净则提示"可能有未纳管的手改"，列出文件，询问是否继续 |
| 1 | **校验**：读 `framework.lock`，比对框架实际 commit | 不匹配则提示升级/回退命令，中止 |
| 2 | **写前快照**：记录将被改写文件的 SHA1 清单 | 存到 `~/shanhe-logs/prewrite-<时间戳>.sha1` |
| 3 | **铺设**：合并 `content/data/*.json` → 框架 `src/data/`；`content/texts/` → 框架 `texts/`；`content/src/*.c` → 框架 `src/` | 逐文件校验落地结果 |
| 4 | **构建**：调 `make`（含宿主机工具保障） | 失败则打印日志路径与 grep 命令 |
| 5 | **验产物**：ROM 存在 + boot-check 通过 | 否则 exit 1 |
| 6 | **反查**：`git -C 框架 status --porcelain` 列出所有被改动文件 | 与第 2 步快照对比，若有"预期外"的改动则高亮警告 |

### 3.2 关键设计约束

- **幂等**：可重复跑。铺设用合并 + 追加，不清空目录、不删上游文件。
- **不静默**：每一步打印实际做了什么（`[merge] characters.json +12 条`、`[skip] 无变化`）。
- **可预演**：`DRY_RUN=1` 只打印将要做什么，不落盘。
- **反查是防呆关键**：第 6 步存在的全部理由——它能在你忘记"应该改 content/"时立刻抓到。

### 3.3 一键还原（回应"怕丢数据"）

新增 `RESTORE=1` 子命令，把框架还原到上游原始状态：

```bash
# 查看框架被改了什么（不改动任何东西）
bash tools/shanhe-build.sh STATUS=1

# 一键还原：丢弃所有写入，回到 framework.lock 指定的上游状态
bash tools/shanhe-build.sh RESTORE=1
#   内部执行：git -C 框架 checkout -- <被改动的路径>
#   等价于你手动跑 git checkout，但会先列出将要还原的文件让你确认
```

**这意味着**：任何时候你都可以"推倒重来"。框架的原始数据永远在 git 里，`RESTORE=1` 只是把它取回来。

### 3.4 JSON 覆盖语义（**已实测，结论明确**）

> 2026-09-25 实地勘察结论。这一节决定了同步脚本的核心策略。

**实测发现**：

| 事实 | 证据 |
|---|---|
| `characters.json` 是**整表**，含全部原版角色 | `"fullCoverage": true`，94 个 `"character"` 条目（含 `CHARACTER_EIRIKA`、`CHARACTER_SETH` 等原版角色） |
| `fullCoverage: true` = **设计容量 256 槽全部要有记录** | `scripts/generated_data/characters/schema.py:94-99`：「toggles the dense `1..256` coverage check... all 256 designators authored」 |
| 生成器读的是**单一路径**的完整表 | `registry.py:102` 注释指明源就是 `src/data/characters.json` |

**这意味着**：不能简单"用你的文件覆盖框架的文件"——**因为你的文件里必须包含全部 256 个槽位**，包括所有原版角色。否则密集覆盖校验直接失败。

**→ 采用解法 b（合并）的正确形态**：

不是"你写一个完整表"，而是：

```bash
# 同步脚本的做法：以框架原表为基底，用你的增量补丁覆盖特定条目
1. 读框架 src/data/characters.json  （94 条原版 + 256 槽骨架）
2. 读 content/data/characters.json   （只含你的原创角色，如 CHARACTER_YU_CONG）
3. 按 "character" 键合并：同名条目用你的替换，新键追加
4. 校验合并后仍是 256 槽完整覆盖
5. 写回框架 src/data/characters.json
```

**好处**：
- 你的 `content/data/characters.json` **只写原创内容**，不抄 94 条原版角色，文件小、可读、diff 干净。
- 框架升级（原版角色数值修正）能自动继承，不会因为你的整表覆盖而丢。
- 这本质上是"把你的人工改动**自动化**了"——手工做的话就是"打开框架文件、找到位置、粘贴进去"。

**同样的策略适用于**：`classes.json`、`items.json`、`supports.json`（同为 `fullCoverage` 风格的表）。

### 3.5 章节类 JSON 语义（**已实测，比全局表简单**）

| 文件 | 实测结构 | 同步策略 |
|---|---|---|
| `chapter_objectives.json` | `{"$schema": "...", "chapters": []}` —— **空数组**，等你按章填 | **追加**：把你的章节记录合并进 `chapters[]` |
| `chN_bundle.json` | 每章一个独立文件，内含该章全部表的引用与依赖声明 | **新增文件**：你新增的章节就是新文件，**零冲突** |
| `chN_units/shops/traps/eventscripts/eventlists.json` | 同上，按章独立 | 同上 |

**结论**：章节内容走「**新增文件 + 追加记录**」路线，**天然无冲突**，比全局表简单。

⚠️ **但有个强约束要注意**：`ch2_bundle.json` 里的 `dependencies` 是**精确声明**——列出该章依赖的所有 `characters`/`classes`/`items`。你新建章节时：

- `dependencies.characters` 必须列出该章用到的**全部角色**（包括你新增的原创角色）
- `dependencies.classes` / `items` 同理
- **缺失、重复、过期、空、超容量、矛盾、循环、无效区域、未知引用都会失败**（框架的 validate 会报）

→ 这是好事：它保证你不会引用到不存在的资源。但意味着**加一章时要一次性把依赖列全**。

**另一个重要细节**：`ch2_bundle.json` 的 `externalReferences` 指向 `src/events/ch2-eventscript.h` 等**手写头文件**——说明章节的**事件脚本实现**（`EventScr_*` 符号的实际内容）需要写在 `src/events/` 下的 C 文件里。这部分**属于引擎层**，是章节制作中唯一需要写代码的环节。

| 章节组成 | 放哪 | 需要写 C？ |
|---|---|---|
| 单位组、商店、陷阱、事件列表 | `src/data/chN_*.json` | 否 |
| 胜利条件、AI 组 | `src/data/chapter_objectives.json` | 否 |
| **事件脚本实现**（`EventScr_*`） | `src/events/chN-eventscript.h` + `.c` | **是** |
| 地图 | `graphics/` + TMX/布局元数据 | 否（用工具编辑） |

## 5. 高价值发现：兵刃三环**可能不用写 C**

勘察时发现 `src/data/weapontriangle.json` 是**纯数据驱动**的：

```json
{ "$schema": "fe8.weapontriangle.v1",
  "rules": [
    { "attacker": "ITYPE_SWORD", "defender": "ITYPE_LANCE", "hitBonus": -15, "atkBonus": -1 },
    ...
  ] }
```

且它有完整的生产链路：
- schema 校验：`scripts/generated_data/weapontriangle/schema.py`
- C 生成：产出 `build/generated/data/data_weapontriangle.c`
- 已编入 ROM：`build/.../src/bmb-weapontriangle.o`

**当前结构 = 两个环**：
```python
GROUPS = (
    ("ITYPE_SWORD", "ITYPE_LANCE", "ITYPE_AXE"),      # 物理环
    ("ITYPE_ANIMA", "ITYPE_LIGHT", "ITYPE_DARK"),     # 魔法环
)
EXPECTED_RULE_COUNT = 12   # 每环 3×2 = 6 条，共 12 条
```

**这对本项目的意义**：
- 你的**兵刃三环**（枪克刀克锤克枪，剑中立）本质就是改 `GROUPS[0]` 的成员与规则 → **改 JSON 即可**。
- 你的**三才法环**（天克地克人克天）对应 `GROUPS[1]`（魔法环）→ 同样改 JSON。
- **但要注意**：`schema.py` 中 `GROUPS` 是**硬编码的封闭列表**（注释说明是刻意为之，不做通配扫描）。若你的"剑中立"需要表达"某类型不参与任何环"，可能需要在 schema 层面小改——**这属于 Phase 2.2 要实测确认的事**。

> **这是本次勘察最有价值的发现**：原文档 §11 把"武器三角改造"列为"必须改写原版的地方"，实际上可能只是个数据文件编辑。风险等级要下调。

## 6. 风险与对策

### 6.1 同步机制风险

| 风险 | 影响 | 对策 |
|---|---|---|
| JSON 是整表替换，覆盖会丢框架自带内容 | 高 | **已实测**，采用"增量补丁合并"（§3.4） |
| ~~新增 `.c` 文件框架不自动编译~~ | ~~中~~ | **已查证：自动编译（wildcard）。但新增文件需 `touch Makefile` 强制重解析**（见 `7.框架架构与机制详解.md` §4.2） |
| 上游频繁更新导致合并困难 | 中 | `framework.lock` 钉死 commit；升级是显式动作，不是自动的 |
| 同步脚本本身写错导致内容丢失 | 中 | DRY_RUN 预演 + 反查步骤 + 内容全在 git 里可回滚 |
| 两边都改同一文件导致冲突 | 低 | 铁律：框架永不手改。反查步骤专门抓这个 |
| 忘记跑同步就直接 `make` | 低 | `shanhe-build.sh` 是唯一入口，不要直接进框架 `make` |

### 6.2 资产风险（§2 新增）

| 风险 | 影响 | 对策 |
|---|---|---|
| **立绘 ID 只有 172 槽且原版已用满** | 高 | 22 名原创角色需**替换**原版槽位，不能新增；先定"哪 22 个原版角色被顶替" |
| **战斗动画是 Manual-only，单位成本最高** | 高 | 大量复用原版 + 调色板派生；只给主角做原创（§2.7.3） |
| **卡片图/半身像/杂兵立绘是 manual-only** | 中 | 避免使用；需要时直接改 `portrait_data.c` |
| 章节地图仅支持 `tmx-safe-v1` 单图层正交子集 | 中 | Tiled 绘制时严守约束（2048 字节缓冲、4096 GID） |
| **地图变更（地形事件变化）是 manual-only** | 中 | 需要"打开闸门变地形"这类设计时，预算额外工时 |
| 法术特效 ID 只有 16 个（`0x80..0x8F`） | 中 | 9 件神器特效**必须精简**，或改走战斗动画路径 |
| 音乐采样内存/声道预算无统一校验器 | 中 | 新 BGM 一次加 1~2 首，实机验证后再加；Demo 先复用原版 |
| `BattleAnim.abbr` 仅 12 字节 | 低 | 命名缩写要短 |
| **误以为"编辑器能导出 = 框架支持"** | 中 | 牢记框架明文规则：编辑器预览/导出**不等于**集成（§2.1） |
| 外部工具被当作构建依赖 | 中 | 框架禁用 FEBuilderGBA/EA/Tiled 进正常构建；它们只能当可选参考工具 |

### 6.3 新增风险：原创资产的"四要素"缺一不可

框架对资产集成的定义是**四者齐备**：

1. 项目自有的源文件包（committed **source** package）
2. 确定性校验/转换（deterministic validation/conversion）
3. 完整的登记/链接接线（complete registration/linker wiring）
4. 一个运行时消费案例（runtime consumption case）

**任何一环缺失，资产就是"躺在磁盘上没进游戏"** —— 而且往往不报错。**这必须写进同步脚本的验证步骤**（map 反查）。
